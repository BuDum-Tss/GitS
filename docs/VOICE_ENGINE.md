# Движок голоса (`agent/services/voice_engine/`)

«Умная» часть голоса живёт в ядре персонажа как отдельный сервис с чёткими функциями. К нему подключаются голосовые адаптеры
(Discord, тонкий аудио-шлюз ПК, позже другие), а сами модели распознавания и синтеза работают в отдельных контейнерах и
вызываются по HTTP. Движок выключен, пока не заданы адреса моделей; прежний модуль `services/voice` (голос ПК на хосте) он не
заменяет и не трогает.

Принцип «сообщение это событие»: фраза участника голосового канала это **событие внимания** `voicechat.utterance`, а не реплика
диалога. Отвечает на неё агент **инструментом** `voice.say`.

## Архитектура

```
 Discord (окружение)     Шлюз ПК (тонкий)      другой адаптер
  VoiceAdapterClient      VoiceAdapterClient     VoiceAdapterClient          <- gits_sdk.voice (SDK)
        |  /voice/ws            |                      |
        +-----------+-----------+----------------------+
                    v   один WebSocket на сессию: JSON-управление + бинарные кадры PCM
 ┌────────────────────────── ядро персонажа (контейнер) ──────────────────────────────────────────┐
 │  server.py  токен шины, hello/welcome, маршрутизация, лимиты                                    │
 │      │                                                                                          │
 │  SessionManager ── VoiceSession (адаптер, говорящие, политика перебивания, очередь реплик)      │
 │      │ звук говорящего                                         ▲ кадры по 20 мс                  │
 │  UtteranceSegmenter (VAD) на КАЖДОГО говорящего      Playback (очередь до 3, replace, ack)       │
 │      │ реплика (PCM)                                           ▲ PCM 16 кГц моно                  │
 │  SttClient ───HTTP───> контейнер STT          TtsClient ───HTTP───> контейнер TTS (ESpeech)      │
 │      │ текст                                                                                      │
 │  events.py: voicechat.utterance ──> Attention.submit("voicechat", event) ──> единый агент         │
 │                                                          агент вызывает voice.say / voice.stop ─┘ │
 │  Playback.ended ──> журнал module_out (voicechat.spoken) ──> память моментов и эпизодов           │
 └──────────────────────────────────────────────────────────────────────────────────────────────────┘
```

Движок ничего не знает о ядре и сети: события уходят через переданные функции (`emit_event`, `journal`, `on_speech`), адаптер для
него это `SessionTransport`. Ядру его подключает `wiring.wire_voice` (см. «Подключение к ядру»).

Модули пакета:

| Файл | Что делает |
|---|---|
| `frames.py` | формат звука (PCM s16le, 16 кГц, моно, кадр 20 мс = 320 отсчётов = 640 байт), `AudioFrame`, нарезка |
| `protocol.py` | проводной формат (код общий с SDK: `gits_sdk/voice/protocol.py`) |
| `vad.py` | `VadDetector`, `EnergyVad`, `SileroVad` (необязательно), `UtteranceSegmenter` |
| `stt.py` | `SttClient`, `HttpSttClient`, `FakeStt`, типизированные ошибки |
| `tts.py` | `TtsClient`, `HttpTtsClient` (контейнер ESpeech), `FakeTts`, разбор WAV и ресемплирование |
| `session.py` | `VoiceSession`, `SessionManager`, `Capabilities`, лимиты |
| `playback.py` | очередь реплик, подача кадров в реальном времени, остановка и подтверждения |
| `engine.py` | фасад `VoiceEngine` |
| `events.py` | события для ядра, определение обращения по имени |
| `tools.py` | инструменты агента `voice.*` |
| `server.py` | WebSocket `/voice/ws` |
| `config.py`, `wiring.py` | настройки из окружения, подключение к ядру |

SDK для адаптеров: `agent/interfaces/workspace/gits_sdk/voice/` (`protocol.py`, `audio.py`, `client.py`, `testing.py`).

## Протокол адаптер ↔ движок (версия 1)

Адрес: `ws://<ядро>:8766/voice/ws` (порт дашборда). Заголовок `Authorization: Bearer <токен шины ядра>` (тот же, что у `/ws`
модулей: `GITS_TOKEN`; в контейнере ядро и адаптер получают его так же, как остальные участники шины). Допускаются те же адреса, что
у шины (петля и `GITS_HUB_ALLOW`). Неверный токен: HTTP 401, чужой адрес: 403. Токены в журналы не пишутся.

### Формат звука

PCM s16le, 16000 Гц, моно. Адаптер приводит к нему свой звук (`gits_sdk.voice.to_16k_mono`, `to_48k_stereo`). Звук идёт кадрами,
`FRAME_MS = 20` мс (640 байт); адаптер может склеить несколько кадров в один бинарный (не больше 200 мс = 6400 байт), движок режет
сам. Кадры воспроизведения движок шлёт ровно по 640 байт (последний дополняется тишиной).

### Бинарный кадр

Заголовок 12 байт, сетевой порядок (`!BBHII`), затем PCM:

| Поле | Размер | Значение |
|---|---|---|
| тип | 1 | `1` звук говорящего (адаптер → движок), `2` звук реплики (движок → адаптер) |
| флаги | 1 | зарезервированы, всегда 0 |
| говорящий | 2 | у типа 1: `idx` из `speaker.join` (1..65535); у типа 2: 0 |
| поток | 4 | у типа 1: 0; у типа 2: `play_id` из `play.start` |
| номер | 4 | счётчик кадров (по говорящему или по реплике), с 0 |

Проверки: тело не пустое, чётной длины, не больше 6400 байт; чужой тип, флаги не 0 или нарушение размера это нарушение протокола.

### Сообщения управления

Текстовые JSON `{"type": "...", ...}` не больше 64 КиБ. Адаптер → движок: `hello`, `speaker.join`, `speaker.leave`,
`speaking.start`, `speaking.stop`, `play.ack`, `bye`. Движок → адаптер: `welcome`, `play.start`, `play.end`, `play.stop`, `leave`,
`error`, `bye`. Сообщение чужого направления или неизвестного типа это нарушение.

| Сообщение | Поля |
|---|---|
| `hello` | `version: 1`, `adapter` (`[a-z0-9_.-]`, до 64), `session` (id канала, до 128), `capabilities {echo_free, can_barge_in, speakers_labelled, direct}`, `format {codec: "pcm_s16le", rate: 16000, channels: 1, frame_ms: 20}` |
| `welcome` | `version`, `session`, `format`, `settings {barge_in: "off" \| "any_speaker", barge_in_ms, lang}`, `limits {max_speakers, max_pcm_bytes}` |
| `speaker.join` | `id` (строка адаптера, например id участника Discord), `name`, `idx` (номер в бинарных кадрах, уникален в сессии), `is_owner`, `is_bot` |
| `speaker.leave`, `speaking.start`, `speaking.stop` | `id`. `speaking.*` только подсказка для состояния: решения движок принимает по звуку |
| `play.start` | `utterance_id`, `play_id`, `text`, `total_ms`; сразу за ним идут кадры типа 2 с этим `play_id` |
| `play.end` | `utterance_id`, `play_id`: все кадры отправлены |
| `play.stop` | `utterance_id`, `reason` (`stop`, `replaced`, `barge_in`, `closed`, `error`): сбросить буфер и остановиться |
| `play.ack` | `utterance_id`, `spoken_upto` (мс реально сыгранного), `reason` (`completed` или причина обрыва) |
| `leave` | адаптеру выйти из канала (инструмент `voice.leave`) |
| `error` | `code` (`protocol`, `limit`, `timeout`, `unauthorized`, `rejected`), `message` |
| `bye` | любая сторона закрывает сессию |

Рукопожатие: первое сообщение `hello` в течение 10 с, иначе `error timeout` и закрытие. Повторный `hello` с id уже открытой сессии
заменяет её (адаптер переподключился); старое соединение закрывается. Нарушение протокола после `welcome` получает `error`;
после 20 нарушений соединение закрывается. Обрыв соединения закрывает сессию (звучащее и очередь заканчиваются причиной `closed`).

### Лимиты

Сообщение управления 64 КиБ, тело кадра 6400 байт, число сессий `GITS_VOICE_MAX_SESSIONS` (4), говорящих в сессии
`GITS_VOICE_MAX_SPEAKERS` (32), текст реплики 800 символов после очистки от разметки, отправка адаптеру не дольше 5 с (иначе
соединение считается мёртвым), необработанных распознаваний на сессию 4 (лишние отбрасываются и считаются).

### Реальное время воспроизведения

Кадры идут адаптеру по 20 мс с опережением `lead_ms = 60` мс (три кадра сразу, дальше по одному в 20 мс); адаптер держит свой
короткий буфер. После последнего кадра движок шлёт `play.end` и ждёт `play.ack` не дольше остатка реплики плюс 1.5 с; без
подтверждения реплика считается сыгранной по расчёту часов. `spoken_upto` из подтверждения главнее расчёта.

## Интерфейс адаптера (SDK)

```python
from gits_sdk.voice import VoiceAdapterClient, to_16k_mono_stream, to_48k_stereo_stream

async def play(frames, uid):                 # frames: async-итератор кусков PCM по 640 байт; вернуть сыгранные мс
    up, played = to_48k_stereo_stream(), 0   # свой ресемплер на реплику: состояние фильтра живёт между кадрами
    async for pcm in frames:
        device.write(up.process(pcm))
        played += 20
    return played

client = VoiceAdapterClient(adapter="discord", session="guild-1:chan-2", echo_free=True, can_barge_in=True,
                            on_play=play, on_stop=lambda uid, reason: device.flush())
await client.start()                         # сам подключается, переподключается и заново объявляет говорящих
await client.wait_ready()
idx = await client.speaker_join("u42", "Маша", is_owner=False)
await client.send_audio("u42", to_16k_mono(chunk_48k_stereo))   # звук КАЖДОГО участника отдельно
```

Возможности (`capabilities`) определяют поведение движка:

- `echo_free`: адаптер не отдаёт движку её собственный голос. У Discord так (поток участника чистый), у ПК с колонками нет.
- `can_barge_in`: адаптер умеет мгновенно оборвать воспроизведение (`on_stop` сбрасывает буфер).
- `speakers_labelled`: говорящие различимы по отдельным потокам (Discord да). Диаризации в движке нет и не нужна.
- `direct`: канал «один на один», обращение по имени не нужно.

`on_play(frames, uid)` возвращает сыгранные мс; клиент сам шлёт `play.ack` (причина `completed` или та, что прислал `play.stop`).
`on_stop(uid, reason)` вызывается сразу при `play.stop`, до возврата `on_play`. `on_leave()` приходит на `voice.leave`.

Ресемплирование: `to_16k_mono(pcm_48k_stereo)`, `to_48k_stereo(pcm_16k)`, `resample(pcm, src, dst, ...)` целиком и
потоковые `to_16k_mono_stream()` / `to_48k_stereo_stream()` (состояние фильтра переносится между кусками, щелчков на границах нет).
Нужен numpy; `audioop` не используется (его нет в Python 3.13).

`FakeAdapter` (`gits_sdk.voice.testing`): готовая заглушка для тестов адаптеров и движка; `tone(ms)` и `silence(ms)` дают «речь» и тишину.

## Как добавить новый адаптер за 6 шагов

1. Выбрать `adapter` (имя `[a-z0-9_.-]`) и id сессии (один голосовой канал, стабильный между переподключениями).
2. Получить токен шины и адрес ядра (`GITS_TOKEN`, `GITS_VOICE_URL` или `GITS_CORE_URL`; `default_url()` строит `/voice/ws`).
3. Создать `VoiceAdapterClient` с честными `echo_free`, `can_barge_in`, `speakers_labelled`, `direct`; перебивание зависит от них.
4. Приводить звук каждого участника к PCM 16 кГц моно (`to_16k_mono_stream`) и слать `send_audio(speaker_id, pcm)`; на вход и выход
   участников канала звать `speaker_join` / `speaker_leave` (до первого звука).
5. Реализовать `on_play` (проиграть кадры в устройство, вернуть сыгранные мс) и `on_stop` (немедленно сбросить буфер).
6. Проверить на `FakeAdapter`-сценариях `test/voice_engine/test_voice_engine_server.py`: фраза доходит событием, реплика играется,
   перебивание останавливает, обрыв закрывает сессию, переподключение восстанавливает говорящих.

## Что движок делает с фразой участника

1. На каждого говорящего свой детектор речи и сегментатор: начало после 60 мс речи подряд, конец после 600 мс тишины
   (`GITS_VOICE_TAIL_MS`), реплики короче 240 мс речи отбрасываются (щелчок, вдох), длиннее 30 с режутся, перед речью берётся
   200 мс звука (первый слог не теряется). `EnergyVad` по уровню кадра (порог `GITS_VOICE_THRESHOLD_DB`, по умолчанию -42 dBFS)
   работает без моделей; `SileroVad` (onnxruntime и файл модели в `GITS_VOICE_SILERO_MODEL`, `GITS_VOICE_VAD=silero`) точнее
   на шуме, при отсутствии зависимостей берётся `EnergyVad`.
2. Реплика уходит в STT (не больше 2 одновременно, фразы одного говорящего по порядку). Ошибка STT: фраза пропадает, считается
   в `stats.stt_errors`, повторов нет. Пустой и «шумовой» текст (одна буква, знаки) событием не становится.
3. Готовая фраза это событие внимания.

## События

### Входящее в ядро: `voicechat.utterance`

Подаётся `Attention.submit("voicechat", event)` (тот же вход конвейера внимания, что у событий модулей, но источник не участник
шины: движок внутри ядра). Объявлять вид в манифесте не нужно (его нет): срочность по умолчанию 1, обращение к ней поднимает
срочность до «сказать» и ставит `needs_reply`.

```json
{"kind": "voicechat.utterance", "text": "Глэдос, ты меня слышишь?",
 "sender": {"id": "u42", "name": "Маша", "is_owner": true},
 "addressed_to_me": true,
 "reply_channel": {"module": "voice", "target": "<session>", "tool": "voice.say"},
 "expires_in_s": 90,
 "data": {"session": "...", "adapter": "discord", "duration_ms": 1830, "language": "ru",
          "speaker": {"id": "u42", "name": "Маша", "is_owner": true}, "needs_reply": true,
          "addressed_reason": "name | one_to_one", "interrupted_me": false}}
```

`addressed_to_me`: обращение по имени или алиасу персонажа (целое слово, допустимо короткое окончание: «Глэдоса», «Глэдосу»;
ё = е) или канал «один на один» (`direct` или в канале один живой собеседник). `interrupted_me`: этот говорящий перебил её
меньше чем 15 с назад. Ответ на фразу это вызов `voice.say`, а не текст реплики.

Примечание для пути обращений из каналов: `reply_channel.tool` называет инструмент ответа (`voice.say`), у голоса нет
инструмента `message`; код, строящий подсказку «Нужен ответ», должен брать имя из `tool`, если оно есть.

### Исходящее в память: `voicechat.spoken`

Когда реплика отзвучала (или оборвана, но хоть что-то прозвучало), движок пишет в журнал событий ядра запись `module_out`
(`module: voicechat`, `tool: voice.say`, `to: <session>`, `own: true`, `event_kind: voicechat.spoken`, `completed`, `reason`,
`spoken_ms`, `interrupted`) с текстом **реально сказанного** (при обрыве начало текста по доле сыгранного). Это тот же вид
записи, что пишет роутер для её сообщений в чаты, поэтому память моментов и эпизодов читает её без изменений.

### Событие речи: `on_speech`

Для всех, кому нужен конец речи (дашборд, будущий потребитель): `{"phase": "started" | "ended", "utterance_id", "session",
"adapter"}`, у `ended` ещё `completed`, `reason`, `spoken_upto` (мс), `total_ms`, `spoken_text`. Причины: `stop`, `replaced`,
`barge_in`, `closed`, `error`. Сейчас ядро на него не подписано (журнал `module_out` достаточен).

## Инструменты ядра

Окружение `voicechat` (модуль `core`, видно в любой среде), риск `auto`:

- `voice.say(text, session?, replace?)`: сказать вслух в голосовом канале. Ставит реплику в очередь и сразу возвращает «поставлено» и
  `uid`; синтеза и конца речи не ждёт. `session` можно опустить, если открыт один канал; при нескольких нужен.
- `voice.sessions()`: какие голосовые каналы открыты, кто в них, говорит ли она, что в очереди, политика перебивания.
- `voice.stop(session?)`: замолчать, очистить очередь.
- `voice.leave(session?)`: попросить адаптер выйти из канала.

Инструменты не помечены `sends`: запись `module_out` пишет сам движок и только про то, что действительно прозвучало.

## Очередь реплик

Протокол речи тот же, что у модуля voice: реплика целиком одним куском. `replace: true` обрывает звучащее и очищает очередь,
иначе реплика встаёт в очередь (до 3 ожидающих; при переполнении вытесняется самая старая с причиной `replaced`).
`stop(at: "now")` обрывает сразу, `stop(at: "segment_end")` даёт договорить звучащей (это одна реплика), очередь очищается в обоих
случаях. Синтез следующей реплики начинается при постановке в очередь.

## Перебивание

Политика сессии `barge_in`: `off` или `any_speaker` (любой говорящий). Срабатывает, когда речь говорящего непрерывна дольше
`barge_in_ms` (400 мс; паузы короче 100 мс не разрывают), а она в этот момент говорит: звучащая реплика обрывается
(`play.stop`, причина `barge_in`), очередь очищается. Повторно в той же реплике не срабатывает.

Политика по умолчанию (`GITS_VOICE_BARGE_IN=auto`): `any_speaker` только если адаптер объявил `echo_free` **и** `can_barge_in`
(Discord), иначе `off` (ПК с колонками: её голос слышен микрофону, она перебивала бы сама себя). Явное `any_speaker` для адаптера
без `echo_free` игнорируется. Будущее: «ворота эха» для ПК (подавление её звука из микрофонного потока), тогда адаптер сможет
объявить `echo_free`.

## HTTP-API моделей

### Распознавание (отдельный контейнер; его пишет другой исполнитель)

```
POST {GITS_STT_URL}/v1/transcribe?lang=ru
Content-Type: application/octet-stream
тело: сырой PCM s16le, 16000 Гц, моно (до 60 с)
-> 200 application/json {"text": "...", "language": "ru", "duration_ms": 1830}
```

Клиент `HttpSttClient`: таймаут `GITS_STT_TIMEOUT_S` (15 с) на весь запрос, повторов нет. Ошибки: `SttTimeout`, `SttUnavailable`
(соединение), `SttServerError` (код не 200, есть `status`), `SttBadResponse` (не JSON или нет `text`), все от `SttError`.
Сервис должен отвечать быстро: пока он занят, лишние фразы сессии отбрасываются.

### Синтез (существующий контейнер ESpeech, `docker/espeech`, `services/f5-tts/f5_server.py`)

```
GET  {GITS_TTS_URL}/health      -> 200, когда модель загружена (503 пока грузится)
POST {GITS_TTS_URL}/tts         JSON {"text", "ref_audio_b64", "ref_text", "speed"}  -> audio/wav (моно, 24 кГц)
```

Клиент `HttpTtsClient` читает референс голоса персонажа один раз (`GITS_TTS_REF_AUDIO` и дословный текст `GITS_TTS_REF_TEXT`),
шлёт его base64, скорость `GITS_TTS_SPEED` (0.5..1.5); необязательные `GITS_TTS_VOICE` и `GITS_TTS_EMOTION` добавляются в запрос,
если заданы (ESpeech их игнорирует). Ответ WAV (PCM 8/16/32 бит или float32, моно или стерео, любая частота) приводится к PCM
16 кГц моно в потоке-исполнителе. Таймаут `GITS_TTS_TIMEOUT_S` (60 с). Ошибки: `TtsTimeout`, `TtsUnavailable`, `TtsServerError`,
`TtsBadAudio`, все от `TtsError`. Текст перед отправкой очищается от Markdown и обрезается до 800 символов по границе предложения.
Сбой синтеза заканчивает реплику причиной `error`, следующая реплика очереди играется.

## Подключение к ядру и настройки

`core_service._run` зовёт `wire_voice(layer, registry)` и отдаёт результат HTTP-серверу (`http_api.set_voice`); при остановке
зовётся `voice.stop()`. Токен и разрешённые адреса те же, что у `/ws`. Движок включён, только если заданы **оба** адреса:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GITS_STT_URL` (или `STT_URL`) | нет | адрес сервиса распознавания |
| `GITS_TTS_URL` (или `TTS_URL`, `ESPEECH_URL`) | нет | адрес сервиса синтеза |
| `GITS_VOICE_ENGINE` | авто | `0` выключает при любых адресах; `1` без адресов остаётся выключенным (причина в `/api/voice`) |
| `GITS_VOICE_LANG` | `ru` | язык распознавания |
| `GITS_VOICE_BARGE_IN` | `auto` | `auto`, `off`, `any_speaker` |
| `GITS_VOICE_BARGE_IN_MS` | 400 | сколько речи подряд считать перебиванием (100..3000) |
| `GITS_VOICE_VAD`, `GITS_VOICE_THRESHOLD_DB`, `GITS_VOICE_SILERO_MODEL` | `energy`, -42, нет | детектор речи |
| `GITS_VOICE_TAIL_MS`, `GITS_VOICE_MIN_SPEECH_MS` | 600, 240 | тишина-конец фразы, минимум речи |
| `GITS_VOICE_MAX_SESSIONS`, `GITS_VOICE_MAX_SPEAKERS` | 4, 32 | лимиты |
| `GITS_STT_TIMEOUT_S`, `GITS_TTS_TIMEOUT_S` | 15, 60 | таймауты |
| `GITS_TTS_REF_AUDIO`, `GITS_TTS_REF_TEXT`, `GITS_TTS_SPEED`, `GITS_TTS_VOICE`, `GITS_TTS_EMOTION` | нет, нет, 1.0, нет, нет | голос персонажа |

Выключенный движок не добавляет ядру ни зависимостей (numpy подгружается только при включении), ни маршрута `/voice/ws`, ни
инструментов; `GET /api/voice` отвечает `{"enabled": false, "reason": "..."}`. Включённый отвечает состоянием: сессии, говорящие,
очередь, счётчики (`frames_in`, `utterances`, `stt_errors`, `barge_ins`, `spoken`, `dropped_utterances`), число подключений и отказов.

## Ограничения и риски

- Живые модели не проверялись: тесты идут на заглушках и локальных тестовых HTTP-серверах. Контейнер STT пишется отдельно.
- `EnergyVad` чувствителен к уровню шума: на шумной линии порог (`GITS_VOICE_THRESHOLD_DB`) подбирается; Silero точнее, но не
  проверен вживую (нужен файл модели `silero_vad.onnx` версии v5 с входами `input`, `state`, `sr`).
- VAD и ресемплинг (небольшие куски numpy) выполняются в цикле событий и укладываются в доли миллисекунды на кадр; ресемплирование
  ответа синтеза идёт в потоке-исполнителе. При десятках говорящих VAD стоит вынести в процесс-исполнитель.
- Эхо: адаптер без `echo_free` перебивание не получает. Если такой адаптер всё же отдаст её голос в микрофонный поток, она может
  распознавать сама себя; адаптер обязан отфильтровать собственное воспроизведение или объявить `echo_free: false`.
- Одна реплика синтезируется целиком (без потокового синтеза): задержка до первого звука равна времени синтеза всей реплики; реплики
  стоит делать короткими (`voice.say` описан так).
- Обращение по имени простое (слово с окончанием до двух букв). Продолжение диалога без повторного имени (окно после её реплики в
  канале из многих людей) не реализовано: в канале «один на один» оно не нужно.
- Событие `voicechat.utterance` идёт через общий конвейер внимания: решение «ответить или промолчать» принимают его правила (R1, R6,
  срочность). Адаптация R1/R6 под этот вид и `reply_channel` лежит на исполнителе пути обращений из каналов.
- Движок хранит сессии в памяти ядра: при перезапуске ядра адаптеры переподключаются сами и заново объявляют говорящих.
- Дашборд показывает состояние движка только через `GET /api/voice`; своей вкладки нет.
