# Менеджер фокуса ядра (ТЗ 18)

Что делает: в каждый момент один модуль (или никто) держит **фокус** агента, то есть работает в своей политике `active`.
Остальные модули живут в фоновых политиках (`background`) и не занимают внимание агента. Решает ядро, исполняет модуль.
Код: `agent/focus.py` (менеджер), `agent/focus_dispatch.py` (проверка ответа LLM). Надстройка над `agent/attention.py`:
внимание оценивает событие (D0–D4), менеджер фокуса решает, переключать ли модуль. Внимание не переписано: хук
`Attention.on_decided` получает каждое решение после `_finish`.

## 1. Что модуль объявляет

В манифесте (`docs/MODULES.md`, раздел «Политики фокуса»):

- `policies`: список `{id, title, focus, transitions, interruptible, safe_points, resources, quiet, purpose}`;
- `default_policy`: id фоновой политики, в которой модуль находится, когда фокуса нет.

Проверяет SDK (`validate_manifest`, при `hello` и при загрузке в ядре). Минимум одна политика с `focus: background`,
`default_policy` обязана быть фоновой. Модуль без `policies` работает как раньше: в ядре он без фокуса, фокус ему не
назначается, его события идут только во внимание.

Статус модуля (тема `state`, поле `data.status`), по которому ядро видит, что происходит:

| поле | смысл |
|---|---|
| `active_policy` | текущая политика; фоновая означает, что задача кончилась и фокус свободен |
| `interruptible` | `false` - сейчас небезопасная точка: переключать нельзя (кроме критических событий) |
| `blocked` | строка с причиной (нет материалов и т.п.): модуль сообщает, что продолжить не может; фокус освобождается |
| `active_goal`, `urgency`, `estimated_remaining_s` | для дашборда и журнала |

## 2. Что модуль должен уметь (запросы ядра)

| запрос | тело | ответ |
|---|---|---|
| `focus.release` | `{reason, task_id, force, event_id, checkpoint: true}` | `{ok: true, checkpoint: {...}}`; модуль отвечает, когда остановился в безопасной точке и сохранил checkpoint. `{ok: false, error}` - отказ, фокус остаётся у него |
| `policy.activate` | `{policy, goal, task_id, event_id, priority, reason}` | `{ok: true, policy}` после перехода |
| `focus.resume` | `{task_id, policy, goal, checkpoint, subgoals}` | `{ok: true, policy}`; если модуль его не знает (`unknown`), ядро делает `policy.activate` с `restored: true` |

Если модуль отвечает `unknown` на `focus.release`, ядро считает его не умеющим освобождать фокус и не переключает.

## 3. Правила по умолчанию (стартовая политика)

Старт ядра: фокус **свободен** (его держит пользователь и разговор). Все модули в своих фоновых политиках.

| случай | что делает ядро |
|---|---|
| Событие модуля с приоритетом ниже 60 | в очередь (`deferred`), переоценка раз в 30 с и при смене контекста; ожидание копит приоритет (старение) |
| Событие с приоритетом 60 и выше, фокус свободен | передача фокуса модулю (`policy.activate` в его активную политику) |
| Событие с приоритетом 60 и выше, фокус занят | переключение только если приоритет не ниже «фокус + 15» (фокус по событию держит 60, по просьбе пользователя 95). Игра, которая держит фокус, не отдаётся обычным событиям |
| Критическое событие (срочность 5), например набег или смерть поселенца | переключение сразу, без дребезга, без LLM, без ожидания. Модуль в фокусе может отказать: тогда событие остаётся в очереди |
| Обычное сообщение Telegram при «не беспокоить» (политика `do_not_disturb`, `quiet: true`, или режим пользователя) | не переключает фокус, остаётся в очереди, оценивается после выхода из режима |
| Пользователь в разговоре с ассистентом (`conversation`, `question`) | обычные события ждут, критические идут |
| Модуль в фокусе сообщил небезопасную точку (`interruptible: false`) | обычные события ждут |
| Модуль в фокусе вернулся в фоновую политику сам (задача кончилась) | фокус свободен; прерванная задача возобновляется, если она актуальна |
| Модуль сообщил `blocked` (например, монтаж без исходников) | фокус освобождается, задача в checkpoint со статусом `blocked`, возобновится после снятия блокировки |
| Модуль отключился | фокус освобождается, задача в checkpoint (возобновится при переподключении модуля) |

Игра (RimWorld) по умолчанию не теряет фокус без причины: её фокус отнимают только критические события другого модуля,
просьба пользователя или закрепление пользователя за другим модулем. Обычные события, даже с приоритетом 60–74, его не
переключают, пока игра держит фокус (запас 15 и дребезг). Игра не запускается ядром: фокус сам по себе игру не
запускает (это правило модуля RimWorld, ТЗ 11e POL-12).

## 4. Протокол переключения

Шаги из раздела 7 исходного документа (`docs/tz/18-source-focus-policies.md`), в журнале видны по именам:

1. **evaluate** - правила (`_gate`): DND, закрепление, разговор, порог, дребезг, запас, безопасная точка. LLM вызывается
   только для неоднозначных событий (близко к порогу или к фокусу, не критические).
2. **check interruption** - переход возможен, если текущая политика допускает переход к целевой (`transitions`; пустой
   список - без ограничений) и модуль в безопасной точке.
3. **checkpoint** - модуль отвечает на `focus.release` своим checkpoint; ядро сохраняет его в памяти и в `focus.json`.
   Шаги release и checkpoint идут одним запросом (решение, см. раздел 9).
4. **release** - `focus.release` текущему модулю. Отказ оставляет фокус у него, событие остаётся в очереди.
5. **activate** - `policy.activate` целевому модулю с выбранной активной политикой.
6. **validate** - ответ `ok: true` и совпадающая политика. Иначе переход отменён, событие в очереди, прерванная задача
   возвращается сразу (если модуль отвечает).
7. **resume or schedule** - когда фокус свободен и нет ждущего важного события, возобновляется задача из checkpoint
   (`focus.resume`).

## 5. Очередь событий

Состояния: `pending` (ждёт оценки), `deferred` (отложено, с условием возобновления), `processing` (идёт переход),
`resolved` (фокус передан или модуль справится сам), `expired` (срок вышел, отложено дольше 30 мин, или `expires` внимания),
`discarded` (слито с другим). Одинаковое событие того же модуля в окне 60 с склеивается (`count`).

Приоритет: базовый приоритет из внимания, плюс старение: каждые 5 мин ожидания +10, не выше 70. Критические не старят.

Сохранность: очередь и checkpoint в памяти ядра, на диск пишутся `memory/focus.json` (в папке памяти ядра, через
`asyncio.to_thread`). Перезапуск ядра не теряет прерванные задачи; очередь восстанавливается без просроченных событий.

Опасное событие (категория `danger`, `death_injury`, `disaster`) с уверенностью классификатора ниже 0,5 не понижается:
сначала перепроверка (`recheck`, если подключена), без результата событие считается важным (приоритет не ниже 60).

## 6. Дребезг

| параметр | значение | что гасит |
|---|---|---|
| `MIN_FOCUS_S` | 20 с | переключение сразу после передачи фокуса (кроме критических) |
| `MAX_SWITCHES_PER_MIN` | 4 | слишком частые переключения |
| `GRACE_S` | 5 с | ложное освобождение фокуса по статусу модуля, который ещё не обновился |
| `RECHECK_S` | 30 с | отложенные переоцениваются раз в 30 с |

## 7. Checkpoint задачи

Поля: `task_id`, `module`, `policy`, `goal`, `priority`, `origin`, `status` (`paused`, `blocked`, `resumed`, `stale`),
`reason`, `resume` (условие: `holder_free`, `module_connected`, `unblocked`), `created`, `attempts`, `subgoals`,
`payload` (то, что вернул модуль, не больше 16 КБ), `scratch` (`<модуль>/scratch`, слот рабочей памяти по ТЗ 04c).
Задача старше 6 ч на паузе становится `stale` и не возобновляется. После трёх неудачных возвратов тоже `stale`.
Модуль без `focus.resume` (RimWorld до ТЗ 18) получает возврат через `policy.activate` с `restored: true`.

## 8. Команды пользователя

- **Закрепить** (`pin`): другие модули не переключают фокус, кроме критических событий. За модуль без фокуса закрепление
  сразу передаёт ему фокус. Снимается повторной командой. Дашборд: кнопка «закрепить» в блоке «Фокус».
- **Не беспокоить** (`dnd`): для всего агента (`all`) или для одного модуля. Сообщения копятся, фокус не переключают.
  Критические события проходят. Дашборд: кнопка «не беспокоить». **Для всего агента это одно состояние с настройкой ядра**
  `dnd` / `quiet_until` (`settings.py`): включил в дашборде, голосом или через фокус - действует везде, и наоборот. Для
  модуля состояние живёт в менеджере фокуса.
- **Профиль**: профиль может объявить `focus.quiet_modules` (список модулей): пока профиль активен, эти модули не переключают
  фокус (обычные события ждут, критические идут). Это вычисляемое значение, в настройки не пишется и не меняет «не беспокоить»;
  пользователь его видит в блоке «Фокус» («профиль не переключает фокус»). Ни один профиль в репозитории пока этого не
  объявляет (решение владельцу, см. ниже).
- **Разовое исключение** (`allow_once`): следующее обычное событие модуля проходит режим; сам режим не отменяется.
- Голосом и в чате: инструмент `focus.control` (окружение `core`, риск `auto`): действия `pin`, `unpin`, `dnd_on`,
  `dnd_off`, `allow_once`. Модуль для закрепления и разового исключения обязателен.
- HTTP (локально): `GET /api/focus`, `POST /api/focus/pin`, `POST /api/focus/dnd`, `POST /api/focus/allow_once`.

## 9. Два эшелона решения (ТЗ 18b)

Решение о событии принимается в два эшелона. Первый всегда работает и дешёвый, второй вызывается редко.

```
событие (внимание: D0-D4, срочность по категории)
   │
   ▼
1. GLiNER (agent/decide.py, служба :8768): вопросы category, addressed, needs_reply,
   focus_needed (нужен ли фокус прямо сейчас) и policy (подсказка «модуль/политика»
   из активных политик подключённых модулей, плюс «none»). Уверенность у каждого ответа.
   │
   ├─ уверенность высокая, подсказка не спорит с правилами → правила решают без LLM  [эшелон gliner]
   ├─ критическое событие (срочность 5) → переключение без ожидания                  [эшелон rules]
   ├─ классификатора нет (сервис выключен или не ответил) → правила по приоритету    [эшелон rules]
   │
   └─ неоднозначно → 2. Gemma (agent/focus_dispatch.py, LM Studio, тайм-аут 5 с)     [эшелон gemma]
```

**Первый эшелон (GLiNER).** Менеджер получает от внимания подсказки в `item.data`: `focus_needed`, `focus_conf`,
`policy_hint` (`модуль/политика` или `none`), `policy_conf`, а также `category_conf` (уверенность категории). Варианты
подсказки политики берёт `FocusManager.policy_options()`: активные политики (`focus: active`) подключённых модулей
с назначением из манифеста (`purpose`, иначе `title`), не больше 12 вариантов. Срочность по-прежнему выводится из категории
(`CATEGORY_URGENCY`): абстрактную срочность модель различает плохо (см. комментарий в decide.py).

**Когда правила однозначны (без LLM).** Событие решают правила, если выполнено всё:
- классификатор не сомневается: уверенность категории не ниже `CONF_LOW` 0.6, а рядом с порогом (или фокусом) - не ниже
  `CONF_HIGH` 0.8;
- подсказка политики не указывает на другой модуль (`_conflict`);
- нет второго претендента с близкой важностью (`_claimant`);
- не критическое событие.

Если классификатора нет совсем (сервис выключен) и событие далеко от порога, решают правила по приоритету, как раньше.
`focus_needed = нет` с уверенностью от 0.8 даёт отложенное событие с причиной «классификатор: событие не требует фокуса».

**Второй эшелон (Gemma).** Вызывается менеджером (`_ambiguity`) только для неоднозначных случаев и только если модель
подключена (`GLADOS_FOCUS_LLM=0` выключает):
1. низкая уверенность классификатора (ниже 0.6);
2. близко к порогу переключения или к фокусу, а уверенности нет или она ниже 0.8;
3. конфликт подсказки: другой модуль, или «фокус не нужен» при важности от 60;
4. два претендента на фокус от разных модулей с разницей меньше запаса 15;
5. перепроверка опасного события (`danger`, `death_injury`, `disaster`) с уверенностью ниже 0.5 (`recheck`): срочность 0-5
   от модели; без ответа событие считается важным (приоритет не ниже 60), как и раньше.

Критические события модель не видит. Запрос: системная инструкция с конечным списком операций и контекст состояния
(очередь до 10 событий, фокус, политики, задачи до 5, закрепление, «не беспокоить»). Ответ разбирается строго: ровно один
JSON-объект (допускается обрамление ```json), иначе ответ отброшен (статус `invalid`). Тайм-аут 5 с (статус
`unavailable`). После сбоя модели пауза 30 с, без повторов на каждом событии. Операции из ответа проверяются
`focus_dispatch.validate` (до 5 операций, конечный список из раздела выше) и применяются менеджером теми же правилами, что и
детерминированный путь: дребезг, запас и безопасная точка остаются в силе. Сбой или невалидный ответ - правила без изменений.
LLM не вызывает методы модулей. Тексты событий в запросе помечены как данные, не как указания.

Эшелон решения записывается в каждую запись журнала решения: `echelon` (`rules`, `gliner`, `gemma`) и `confidence`
(уверенность категории), а также `hint` (подсказка политики). Эшелон `gemma` ставится, если диспетчер ответил принятой
операцией или перепроверкой; `gliner`, если классификатор дал ответ, а правила решили по нему; `rules` - иначе.

## 10. Аудит

Каждый шаг пишется в журнал событий `focus` (`events_log`) и в память для дашборда (последние 300): вид записи
(`enqueue`, `merge`, `aging`, `defer`, `resolve`, `expired`, `checkpoint`, `release`, `activate`, `switch`, `resume`,
`llm`, `llm_op`, `recheck`, `request`, `pin`, `dnd`, `once`), событие, модуль, приоритет до и после, причина, условие
возобновления, эшелон решения (`echelon`), уверенность (`confidence`), подсказка политики (`hint`), почему вызвана модель
(`why`), ответ диспетчера и результат проверки. Блок «Фокус» дашборда показывает эшелон у держателя фокуса, в очереди и в
журнале.

## 11. Константы

`MIN_FOCUS_S=20`, `MAX_SWITCHES_PER_MIN=4`, `GRACE_S=5`, `AGING_S=300`, `AGING_STEP=10`, `AGING_CAP=70`, `RECHECK_S=30`,
`EVENT_TTL_S=1800`, `DEDUPE_S=60`, `CHECKPOINT_MAX_AGE_S=6*3600`, `RESUME_RETRIES=3`, `REFUSE_BACKOFF_S=60`,
`LLM_TIMEOUT_S=5`, `CONF_LOW=0.6`, `CONF_HIGH=0.8`, `MAX_POLICY_OPTIONS=12`. `agent/focus_dispatch.py`: `CALL_TIMEOUT_S=5`,
`COOLDOWN_S=30` (пауза после сбоя модели), `MAX_TOKENS=400`. Модель та же, что у быстрого слоя (`fast_brain`, LM Studio,
`GLADOS_FAST_MODEL`); выключатель второго эшелона: `GLADOS_FOCUS_LLM=0`.

Отказ модуля в `policy.activate` ставит целевому модулю паузу в 60 с: в это время его события не отпускают фокус прежнего
владельца (иначе игра ставилась бы на паузу и возвращалась впустую).

## 12. Чего пока нет

- Ресурсы политик (`resources`: gpu, cpu, tokens) принимаются и описываются, но не ограничивают фоновые операции.
- Политика `quiet` - расширение протокола (в исходном документе такого поля нет): в ТЗ 18 описан режим «не беспокоить»,
  но не способ его объявить модулем.
- Профили не объявляют `focus.quiet_modules` (поле готово, решение за владельцем).
- Модель Gemma вызывается только при запущенной LM Studio; без неё работают правила и GLiNER.
- Трасса ТЗ 17 (`trace.py`) и рабочая память ТЗ 04c (`working_memory.py`) в репозитории не существуют: checkpoint
  хранится в самом менеджере (имя слота `<модуль>/scratch`) и в `focus.json`.
- Модули Telegram, голос, питомец и рабочий стол объявляют фоновые политики, но не умеют переходить в активные
  (`policy.activate` у них не реализован). Фокус им не назначается, пока модули не реализуют переходы.
- Монтаж (`modules/montage`): манифест правится в его папке (см. CHANGELOG).
