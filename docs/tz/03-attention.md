# 03. Менеджер внимания: классификатор, динамическая важность, фокус, очередь речи

Этап 1. Репозиторий: `GitS`. Ветка: `tz/03-attention` (от ветки с выполненным ТЗ 02).
Читать перед этим: `00-architecture.md`, `01-module-contract.md`, `02-core.md`. Справочно — прежний дизайн
`docs/attention-graph.html` (идеи приоритетов P0–P3 и безопасных точек прерывания взяты оттуда; LangGraph не
используется).

## 1. Цель

Она реагирует быстро, говорит по делу и сама замечает поводы, но не болтает попусту и не теряет важное. Для этого
каждое событие любого модуля, каждая речь модуля, вопрос и собственная проактивная реплика проходят через один
менеджер внимания, который:
1. быстро оценивает событие (правила + классификатор GLiNER2.5-multi-Decide);
2. умножает оценку на вес контекста (профиль, отправитель, состояние пользователя, временные правила, свежесть);
3. решает: выбросить, отложить в сводку, сказать при случае, сказать скоро, прервать текущее;
4. ведёт единую очередь речи и стек фокуса.

## 2. Объём

Входит: `agent/decide.py` (классификатор), полная реализация `agent/attention.py` (интерфейс из ТЗ 02 §9.4),
очередь речи, стек фокуса, сводка, временные правила и инструменты `attention.*`, быстрые пути «замолчи» и
классификация обращений для маршрутизатора, журнал решений, настройки, тесты.

Не входит: дообучение классификатора; перенос модулей; изменение характера.

## 5. Путь события

- **ATT-6 (ОБЯЗАТЕЛЬНО).** Склейка: событие с `dedupe_key`, который уже был за последние 60 с и ещё не озвучен, не
  создаёт новый `Item`: `count += 1`, `text` заменяется новым.
- **ATT-7 (ОБЯЗАТЕЛЬНО).** Правила до классификатора (в этом порядке; первое сработавшее определяет исход):
  - **R1 Обращение владельца.** `sender.is_owner` и (`addressed_to_me` или канал — личка ей) и есть `reply_channel` →
    это `UserInput(kind=module)` для разговора (ТЗ 02 CORE-24), не событие внимания.
  - **R2 Ответ на вопрос.** Есть ожидающий вопрос (`approvals`), а событие — от владельца в канале, где вопрос задан →
    в `approvals` как ответ.
  - **R3 Временное правило `mute`** совпало (раздел 9) → решение D1 (в сводку), классификатор не вызывается.
  - **R4 Критично.** `urgency_hint == 5` и `kind` объявлен в `emits` модуля с `default_urgency == 5` → `urgency = 5`
    без классификатора.
- **ATT-8 (ОБЯЗАТЕЛЬНО).** Базовая срочность `urgency` (0–5): максимум из `urgency_hint` (или `default_urgency` из
  манифеста) и срочности по категории классификатора (`CATEGORY_URGENCY`, ATT-4; если классификатор вызывался и
  уверенность выше порога; категория `spam` даёт 0 независимо от подсказки). `needs_reply` и `addressed` — от
  классификатора, если
  модуль не задал явно. Если классификатор вернул `None` — подсказки модуля, по умолчанию `urgency = 1`,
  `needs_reply = False`.

## 6. Динамическая важность

- **ATT-9 (ОБЯЗАТЕЛЬНО).** Формула (все множители и пороги — из настроек `attention`, значения по умолчанию ниже):

```
priority = clamp( urgency * 20 * w_profile * w_sender * w_rule * w_user * freshness , 0, 100 )
```

| Множитель | Как считается | По умолчанию |
|---|---|---|
| `w_profile` | `attention.weights` активного профиля: шаблоны по `kind` (`fnmatch`), берётся самый длинный совпавший шаблон | 1.0 |
| `w_sender` | владелец 1.5; человек из `relationships` с близостью ≥ 0.6 — 1.3; известный человек — 1.0; неизвестный — 0.8; нет отправителя — 1.0 | см. слева |
| `w_rule` | произведение весов действующих временных правил (раздел 9); `only` для несовпавших событий того же модуля — 0.2 | 1.0 |
| `w_user` | «не отвлекать» (`dnd` или `quiet_until > now`) — 0.3, кроме `urgency == 5` с `addressed_to_me`; пользователь отошёл (простой ввода > 600 с) — 1.0, но решения D2–D4 превращаются в D1 (сказать некому), кроме вопросов (идут в Telegram по ТЗ 01 §7.3) | 1.0 |
| `freshness` | `0.5 ** (age / half_life)`; `half_life` по виду: события игры 60 с, Telegram 900 с, экран 120 с, задачи 600 с, прочее 300 с (шаблоны в настройках) | см. слева |

  Вес отправителя ищется: `sender.id` → запись `relationships` (если модуль передал `tg:<id>`, сопоставление по
  `relationships` и памяти контактов; если записи нет — «неизвестный»).
- **ATT-10 (ОБЯЗАТЕЛЬНО).** Решение по `priority` (пороги `[15, 35, 60, 85]`, запас прерывания 15):

| Решение | Условие | Что происходит | Аналог P |
|---|---|---|---|
| D0 выбросить | `< 15` | только журнал | — |
| D1 в сводку | `15 ≤ p < 35` | в буфер сводки модуля; `memorable` → очередь графа памяти | P3 |
| D2 сказать при случае | `35 ≤ p < 60` | кандидат речи с этим приоритетом, срок жизни = `expires` или 10 мин | P2 |
| D3 сказать скоро | `60 ≤ p < 85` | кандидат речи; прерывает только «болтовню» (кандидатов < 35) | P1 |
| D4 прервать | `p ≥ 85` или (`p ≥ 60` и `p > focus.priority + 15`) | новый фокус «реакция» (раздел 8), речь прерывает текущую на границе предложения | P0 |

- **ATT-11 (ОБЯЗАТЕЛЬНО).** Если `needs_reply` и есть `reply_channel` и решение D2–D4 — в факт для речи добавляется
  пометка «на это можно ответить через <модуль>» (факт, не фраза). Отвечает она только по просьбе пользователя
  (маршрутизатор и инструмент модуля с его риском). Самостоятельных ответов в чужие чаты нет.
- **ATT-12 (ОБЯЗАТЕЛЬНО).** Задачи модулей (`on_job_update`): `waiting_user` → вопрос (раздел 7.3); `done` → urgency 3;
  `failed` → urgency 4; прочие смены стадии → urgency 1 (в сводку). Дальше — общая формула.

## 7. Очередь речи

```python
@dataclass
class SpeechCandidate:
    id: str
    source: str            # "conversation" | "module:<id>" | "attention:<item id>" | "proactive" | "question"
    mode: str              # "verbatim" | "fact"
    text: str
    emotion: str | None
    priority: int          # 0..100
    created: float
    expires: float
    key: str | None        # одинаковые key: остаётся новейший
```

- **ATT-13 (ОБЯЗАТЕЛЬНО).** Единственная точка, откуда звучит речь, — планировщик очереди речи. Все пути
  (ответ разговора, `say` модулей, факты внимания, проактивные реплики `companion.proactive_loop`, вопросы) кладут
  кандидатов в очередь; `companion._speak_about` и `companion.say` вызываются только планировщиком. Ответ на
  обращение пользователя — `priority = 95`, `source = "conversation"`.
- **ATT-14 (ОБЯЗАТЕЛЬНО).** Планировщик выбирает кандидата с наибольшим приоритетом (при равенстве — старший), когда
  все условия выполнены:
  1. сейчас не говорит (`SpeechOutput.is_speaking()` ложно);
  2. пользователь не говорит и закончил говорить ≥ 1,5 с назад (`presence.user_speaking`, `last_user_ts`);
  3. не ждёт ответа на заданный вопрос (кроме кандидатов `conversation`);
  4. с последней самостоятельной реплики прошло ≥ `min_gap` (тихо 90 с, обычно 30 с, болтливо 10 с — по настройке
     `chattiness`); не действует для `conversation`, `question` и `priority ≥ 85`.
- **ATT-15 (ОБЯЗАТЕЛЬНО).** Устаревшие кандидаты (`now > expires`) удаляются с записью в журнал. Срок по умолчанию:
  `conversation` 120 с, `verbatim` от модуля 20 с (если не задан), факт события — `expires` события или 600 с,
  проактивные — 60 с.
- **ATT-16 (ОБЯЗАТЕЛЬНО).** Повторы: кандидат, текст которого повторяет недавно сказанное (существующая проверка
  `companion._repeats_recent`), удаляется.
- **ATT-17 (ОБЯЗАТЕЛЬНО).** Прерывание: если пришёл кандидат с `priority ≥ 85`, а сейчас звучит кандидат с приоритетом
  меньше на 15 и более — `SpeechOutput.stop(utterance_id)` (реализация останавливает на границе текущего предложения,
  ТЗ 12), прерванный кандидат не возвращается в очередь; затем звучит новый.
- **ATT-18 (ОБЯЗАТЕЛЬНО).** Быстрый путь «замолчи»: обращение пользователя с `intent == "stop"` (или совпадение с
  нынешними правилами тишины в `companion`) → немедленно `SpeechOutput.stop(None)` и очистка очереди от кандидатов
  ниже 85, до вызова LLM. Дальше — как сейчас (`_set_quiet`).

### 7.3. Вопросы

- **ATT-19 (ОБЯЗАТЕЛЬНО).** `submit_question` (из `core.ask` и вопросов задач): кандидат речи `source="question"`,
  `priority = clamp(urgency_hint*20, 40, 90)` (по умолчанию 60), с фактом вопроса для модели. Вопрос считается
  заданным, когда прозвучал (или показан в чате при `voice_muted`); с этого момента `approvals` ждёт ответа. Если
  пользователь отошёл (простой > 600 с) и включён `telegram` и модуль Telegram подключён — вопрос уходит владельцу в
  Telegram (`deliver` с `target: "owner"` модулю с `chat.channel`), ответ оттуда приходит правилом R2.

### 7.4. Объявления о долгих запусках (AN-1…AN-3, правило 14 README)

Решение владельца 2026-10-11: каждое объявление о долгом запуске обязано прозвучать. Через формулу важности они не годятся
(`urgency_hint 3` даёт ровно 60, а свежесть опускает ниже порога), поэтому у них свой вид кандидата.

- **AN-1 (ОБЯЗАТЕЛЬНО).** Кандидат речи `source="announce:<id>"` (`family == "announce"`): приоритет 75 (выше болтовни и D2,
  ниже прерываний от 85: текущую реплику не обрывает, кроме «болтовни», а звучит сразу после неё), срок жизни 180 с, `min_gap`,
  проверка повторов (ATT-16) и ожидание ответа на вопрос его не задерживают. Одинаковые (по тексту) объявления одного источника
  в пределах 20 с от первого склеиваются в одно, счётчик идёт в факт; повтор уже озвученного в этом окне не озвучивается.
  Устаревшее и снятое «замолчи» объявление попадает в сводку.
- **AN-2 (ОБЯЗАТЕЛЬНО).** В очередь как `announce`, минуя формулу и временные правила, идут: `POST /api/notify`; `say` модуля и
  событие с `announce: true`; событие вида `<модуль>.launch`. Решение `ANNOUNCE` пишется в журнал `attention` (поле `route`:
  `speech`, `short`, `digest`). «Не отвлекать» (`dnd`, `quiet_until`): звучит, но в факте пометка «коротко» (готовую реплику
  `verbatim` не сократить). Пользователь отошёл (простой > `away_after_s`): объявление уходит в сводку и журнал, не в Telegram.
- **AN-3 (ОБЯЗАТЕЛЬНО).** SDK: `validate_say` и `validate_event` принимают `announce: bool`, `client.say(..., announce=True)`,
  `client.event(..., announce=True)`. Манифест: у инструмента `announce: true` (ТЗ 01 §6.1); ядро перед вызовом `tool.call`
  (`module_registry`) объявляет «запускаю <name>: <первое предложение описания>. Аргументы: <короткие значения>» через
  `Attention.submit_announce`; параметры из `core_fills` в объявление не попадают, сбой объявления вызов не останавливает.

## 8. Стек фокуса

```python
@dataclass
class Focus:
    id: str
    kind: str          # "idle" | "conversation" | "reaction" | "question"
    topic: str         # факт: о чём
    source: str
    priority: int
    started: float
    last_active: float
    resumable: bool
```

- **ATT-20 (ОБЯЗАТЕЛЬНО).** Дно стека — `idle` с приоритетом 0, снимать нельзя. `conversation` кладётся при обращении
  пользователя (приоритет 90) и снимается через 60 с без новых обращений после её последнего ответа. `reaction`
  кладётся решением D4 (приоритет = `priority` события) и снимается, когда реплика по нему прозвучала (или устарела).
  `question` — пока ждёт ответа на вопрос.
- **ATT-21 (ОБЯЗАТЕЛЬНО).** Глубина не больше 3 (кроме `idle`): при переполнении удаляется самый старый
  `resumable` элемент.
- **ATT-22 (ОБЯЗАТЕЛЬНО).** Возврат: когда снимается верхний фокус и открывается прерванный `conversation` моложе
  300 с — в очередь речи кладётся факт «разговор о <topic> прервался из-за <topic прервавшего>» с приоритетом 40;
  возвращаться ли к теме, решает модель (она может промолчать — пустой ответ модели допустим).
- **ATT-23 (ОБЯЗАТЕЛЬНО).** `presence.focus` = `"<kind>: <topic>"` верхнего фокуса, `presence.busy` = верхний фокус не
  `idle`.

## 9. Временные правила и инструменты

```python
@dataclass
class Rule:
    id: str                  # "r-" + 6 hex
    module: str | None       # "telegram"
    kind: str | None         # шаблон fnmatch: "telegram.*"
    sender: str | None       # подстрока имени отправителя, без регистра
    effect: str              # "mute" | "boost" | "only" | "normal"
    until: float
    created_from: str        # реплика пользователя, из которой правило создано
```

Эффекты: `mute` — совпавшие события в сводку (R3); `boost` — `w_rule = 2.0`; `only` — совпавшие `w_rule = 1.5`,
несовпавшие события того же модуля (или всех модулей, если `module` не задан) `w_rule = 0.2`; `normal` — отменить
прежние правила для того же совпадения.

- **ATT-24 (ОБЯЗАТЕЛЬНО).** Инструменты ядра (окружение `core`, `availability: always`, `risk: auto`):

| id | params | Что |
|---|---|---|
| `attention.set_rule` | `module` (string, enum подключённых модулей, необяз.), `kind` (string, необяз.), `sender` (string, необяз.), `effect` (enum `mute`/`boost`/`only`/`normal`), `minutes` (integer, 1–1440, по умолчанию 60) | создать правило; описание для планировщика: «пользователь просит не отвлекать, заглушить, выделить кого-то или что-то на время: "пока играю, из телеги только мама", "час не трогай меня с чатами"» |
| `attention.rules` | — | действующие правила (`informative`) |
| `attention.clear_rules` | `id` (string, необяз.) | снять одно или все |
| `attention.digest` | `module` (string, необяз.) | что накопилось в сводке (`informative`); после выдачи буфер очищается |

  Хотя бы одно из `module`, `kind`, `sender` обязательно (иначе `ToolError`). Правила хранятся в
  `memory/attention_rules.json` (переживают перезапуск), просроченные удаляются при загрузке и раз в минуту.
- **ATT-25 (ОБЯЗАТЕЛЬНО).** Обращение с `intent == "attention_rule"` идёт в маршрутизатор как действие (без
  предварительной проверки `looks_like_action`).

## 10. Сводка

- **ATT-26 (ОБЯЗАТЕЛЬНО).** Буфер сводки на каждый модуль, до 50 записей (старые вытесняются), туда попадают D1 и
  устаревшие нерассказанные D2.
- **ATT-27 (ОБЯЗАТЕЛЬНО).** Сама предлагает сводку: когда фокус вернулся в `idle` после `conversation` или `reaction`,
  в буферах ≥ 3 записей с исходным `priority ≥ 25`, и за последние 10 минут не было самостоятельных реплик — в очередь
  речи факт «накопилось: <краткий список фактов>» с приоритетом 40. Сводка в речи — не больше 5 фактов, самые важные.

## 11. Обращения пользователя и маршрутизатор

- **ATT-28 (ОБЯЗАТЕЛЬНО).** Каждое обращение (`UserInput`) классифицируется `INPUT_SCHEMA` до маршрутизатора:
  - `stop` → ATT-18;
  - `approval` при ожидающем вопросе → `approvals` (как сейчас `_answer_approval`, классификатор — дополнительный
    признак, а не замена);
  - `chat` и не `Router.looks_like_action(text)` → маршрутизатор не вызывается (экономия вызова Gemma);
  - `action`, `attention_rule` или `looks_like_action` → маршрутизатор как сейчас;
  - `about_self` → разговор с `registry.describe()` в контексте (как сейчас при «не могу»);
  - `needs_memory == "no"` → поиск в личной памяти для этой реплики пропускается (ТЗ 04 использует этот признак).
  При недоступном классификаторе — нынешнее поведение без изменений.

## 12. Журнал и настройки

- **ATT-29 (ОБЯЗАТЕЛЬНО).** Каждое решение пишется в `events_log` (вид `attention`): `item`, `module`, `kind`,
  `urgency`, все множители, `priority`, решение, время классификатора в мс, первые 200 символов текста.
- **ATT-30 (ОБЯЗАТЕЛЬНО).** Настройки (`settings.DEFAULTS["attention"]`, словарь, глубокое слияние как у `modules`):
  `{"classifier": true, "thresholds": [15, 35, 60, 85], "interrupt_margin": 15, "away_after_s": 600,
  "half_life": {"rimworld.*": 60, "telegram.*": 900, "desktop.*": 120, "*.job": 600, "*": 300}}`. В дашборде —
  переключатель классификатора и пороги на вкладке «Состояние», список действующих правил с кнопкой «снять».

## 13. Производительность

- **ATT-31 (ОБЯЗАТЕЛЬНО).** Путь события без классификатора (правила, формула, решение) ≤ 5 мс. Классификатор: замерить
  p50 и p95 на 200 типичных текстах до 400 символов на машине пользователя и записать в отчёт и `CHANGELOG`. Цель
  p95 ≤ 400 мс на CPU (в rimworld намерено ~300 мс на событие). Если цель не достигнута — сообщить в отчёте (не оптимизировать в рамках этого ТЗ).
- **ATT-32 (ОБЯЗАТЕЛЬНО).** Ни один вызов классификатора не блокирует цикл событий (асинхронный HTTP-клиент с тайм-аутом, ATT-3).
  При очереди к классификатору длиннее 20 событий новые события без `urgency_hint` получают `urgency = 1` без
  классификатора (с пометкой в журнале).

## 14. Тесты

- **ATT-33 (ОБЯЗАТЕЛЬНО).** `Decider` подменяется заглушкой с заданными ответами. Тесты:
  - формула и каждый множитель отдельно; самый длинный шаблон веса профиля; `freshness`;
  - каждое правило R1–R4; склейка по `dedupe_key`;
  - каждое решение D0–D4 на пограничных значениях порогов; D4 по запасу над фокусом;
  - очередь речи: выбор по приоритету, условия 1–4 из ATT-14, `min_gap` по `chattiness`, устаревание, повторы,
    прерывание (ATT-17), «замолчи» (ATT-18);
  - стек фокуса: глубина, снятие `conversation` по тайм-ауту, возврат к прерванному (ATT-22);
  - временные правила: каждый эффект, срок, сохранение и загрузка, инструмент без условий → `ToolError`;
  - сводка: накопление, вытеснение, самостоятельное предложение (ATT-27), `attention.digest`;
  - вопрос пользователю: озвучен → ожидание → ответ; пользователь отошёл → `deliver` в Telegram-модуль (заглушка);
  - классификатор недоступен → нынешнее поведение.
  Время подменяется (фиктивные часы), без `sleep`.

## 15. Приёмка

1. `.\check.ps1` зелёный.
2. Ручная проверка с эхо-модулем: событие `echo.ping` с `urgency_hint` 1, 3, 5 даёт решения D1, D2, D4
   соответственно (видно в журнале и дашборде); при «не отвлекать» D2 становится D1, а 5 с `addressed_to_me` звучит.
3. Во время её длинной реплики «замолчи» обрывает речь до конца текущего предложения.
4. «Следующий час не отвлекай меня эхо-модулем» создаёт правило, видно в дашборде, события эхо-модуля уходят в сводку;
   «что я пропустила?» выдаёт их.
5. Замеры классификатора записаны в CHANGELOG.
