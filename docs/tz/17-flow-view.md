# 17. Проверка ядра без модулей и схема потока данных во вкладке «Состояние»

Этап 4. Репозиторий: `GitS`. Ветка: `tz/17-flow-view` от `master` (после слияния ТЗ 15 и ТЗ 16: те же файлы дашборда).
Решение владельца (2026-10-11). Читать вместе с `04c-working-memory.md`.

## 1. Ядро работает само по себе

- **FLOW-1 (ОБЯЗАТЕЛЬНО).** Режим «только ядро»: переменная `GITS_NO_MODULES=1` (и настройка в дашборде) запрещает супервизору
  запускать модули и службы, кроме нужных ядру (decider можно отключить отдельно: без него ядро использует запасные правила).
  Ядро стартует без исключений, дашборд открывается, чат через дашборд отвечает (если модели доступны) или честно сообщает, чего нет.
- **FLOW-2 (ОБЯЗАТЕЛЬНО).** Скрипт `tools/soak_core.py`: поднимает ядро на свободном порту с временной папкой памяти, без модулей,
  10 минут (параметр) шлёт реплики в чат и события через клиентов SDK, подключает и отключает фиктивные модули (в том числе
  роняя соединение), раз в 10 с снимает: потребление памяти процессом, задержку цикла событий, число ошибок в журнале,
  размеры очередей (речь, внимание, память-граф). Критерии: ни одного необработанного исключения, рост памяти < 50 МБ, задержка
  цикла событий p99 < 200 мс, очереди не растут без предела, ядро корректно закрывается. Отчёт в `docs/CORE_SOAK.md`.
- **FLOW-3 (ОБЯЗАТЕЛЬНО).** То же с настоящими модулями telegram/voice/pet в режиме заглушек, если они это поддерживают;
  убийство и перезапуск модуля не роняет ядро.

## 2. Трасса данных (trace)

- **FLOW-4 (ОБЯЗАТЕЛЬНО).** `agent/trace.py`: шина трассы. `trace.step(turn, node, edge_from, edge_to, kind, ms=None, size=None, label="")`.
  Кольцевой буфер 5000 записей, потокобезопасный, не блокирует (накладные расходы < 50 мкс на запись, тест). **Содержимое
  сообщений не записывается**: только тип, размер, id хода, короткая метка (категория, имя инструмента, модуль). Режим «показать
  текст» включает только владелец в настройках и только до перезапуска.
- **FLOW-5 (ОБЯЗАТЕЛЬНО).** Точки трассы (минимум):
  - вход события от модуля (`module_hub`);
  - классификатор GLiNER (`decide.py`): вход — вид и источник, длина текста; выход — категории, срочность, мс;
  - решение внимания D0–D4 и фокус (`attention.py`), очередь речи;
  - обращение к памяти: чтение (слой, область, размер запроса, число попаданий, мс), запись (слой, область, тип);
  - вызов LLM: модель (Gemma / Claude), роль (речь, план, долгая задача), токены, мс;
  - вызов инструмента: имя, модуль, риск, мс, результат ok/error;
  - ответ в канал (голос, Telegram, питомец, дашборд).
  У каждого хода общий `turn`, чтобы путь можно было проиграть.
- **FLOW-6 (ОБЯЗАТЕЛЬНО).** `GET /api/flow` (топология и счётчики) и `GET /api/flow/stream` (SSE, живая трасса). Счётчики по ребру:
  событий в минуту (окна 1 мин и 10 мин), последняя и p95 задержка, доля ошибок.

## 3. Схема (топология)

Описана данными в `agent/flow_spec.py` (узлы, рёбра, слой каждого): код дашборда ничего не знает про конкретные узлы.
Слои (разные цвета из дизайна дашборда, переключаются чекбоксами):

1. **Модули** (вход и выход): telegram, голос (слух), rimworld, desktop, pet, монтаж и любые подключённые; узлы создаются по манифесту.
2. **Внимание:** шина событий → классификатор GLiNER (что принял, какие категории и срочность выдал) → менеджер внимания
   (решения D0–D4, фокус, очередь речи, дайджест).
3. **Мышление:** Gemma (речь, план), Claude (долгие задачи), выбор инструментов (`tool_search`, профили, `always`/`profile`).
4. **Инструменты:** группы по модулям, на ребре частота вызовов.
5. **Память кратковременная:** рабочая память (см. 04c): диалог, внимание, мир модуля, события модуля.
6. **Память долговременная:** личная (граф), справочник (RAG), опыт; области по модулям.
7. **Речь и вывод:** очередь речи → голос / питомец / Telegram / дашборд.

**Поведенческий граф** (аналог LangGraph без самого LangGraph): состояния хода
`принято → классифицировано → решено → (память) → (LLM) → (инструмент, цикл) → ответ или молчание`.
Переходы и условия объявлены в `flow_spec.py` (например, «D2 → молчание», «нужна память → чтение»). В дашборде выбранный ход
подсвечивает путь по переходам: список последних ходов слева, клик показывает путь, задержки по шагам и итог.

- **FLOW-7 (ОБЯЗАТЕЛЬНО).** Вкладка «Состояние»: блок «Поток данных» (Cytoscape уже есть в дашборде), слои, импульс по ребру при
  записи трассы, подписи рёбер с частотой, «пауза» и «проиграть ход».
- **FLOW-8 (ОБЯЗАТЕЛЬНО).** Панель узла по клику: что принял (виды, источники, размер), что выдал (для классификатора:
  категории и срочность; для внимания: решение; для планировщика: выбранные инструменты), частота и задержки, последние 20
  записей (без текста). Для узла памяти: число запросов, попаданий, записей, область.
- **FLOW-9 (ЖЕЛАТЕЛЬНО).** Экспорт трассы хода в JSON.
- **FLOW-10 (ОБЯЗАТЕЛЬНО).** Тесты: топология согласована с реестром модулей (нет узла без ребра), трасса не содержит текста
  сообщений (тест на подставной строке), окна счётчиков, нагрузка 1000 записей в секунду не роняет цикл событий.

## 4. Приёмка

`check.ps1` зелёный; `tools/soak_core.py` проходит критерии; вкладка «Состояние» показывает слои; во время разговора в чате видно,
как импульс идёт события → классификатор → внимание → память → LLM → инструмент → речь; панель классификатора показывает вход и
результат; снимки экрана в отчёт. Коммиты на английском с `Co-Authored-By`, без push, `CHANGELOG.md`.

## Статус реализации
Сделано (ветка `tz/17-flow-view`, влита): трасса `flow_trace.py`, топология `flow_spec.py`, эндпоинты `/api/flow*`, блок «Поток данных» на Cytoscape во вкладке «Состояние», режим «только ядро» (`GITS_NO_MODULES=1`).

Хвосты (ветка `chore/soak`): FLOW-2 и FLOW-3 - `agent/tools/soak_core.py` (прогон настоящего ядра на заглушках модели и речи: реплики в чат, события и обрывы фиктивных модулей через SDK, очередь графа-заглушка; раз в N секунд RSS, лаг цикла событий, число задач, ошибки в журнале, очереди речи, внимания и графа; с `--real-modules telegram,voice,pet` поднимает настоящие модули с `GITS_VOICE_FAKE=1`, `GITS_PET_HEADLESS=1`, убивает процессы и проверяет перезапуск), результаты короткого прогона в `docs/CORE_SOAK.md`, тесты `agent/tests/test_soak_core.py`. Точки трассы: Claude (`analysis.analyze`, `web_search.search`, `Companion.run_claude`: ребро `planner->claude`, ошибки видом `error`), Telegram (`ConversationIO.deliver`: `speech_queue->out_telegram`, успех и сбой), питомец (`Outbound`: присутствие подключённому питомцу, `speech_queue->out_pet`). Ошибки GLiNER отдельно: `decide.last_failure` (down, timeout, error), `Decider.last_error`, шаг вида `error` с меткой `error:<причина>`, `flow_trace.node_errors` и `error_nodes`, поле `errors` в `GET /api/flow`, `error_info` в панели узла, красная пунктирная рамка узла на схеме и блок «Ошибок: N» в панели. Настройка «Только ядро» (`only_core`, раздел «Для разработчиков» настроек): работает как `GITS_NO_MODULES=1`, применяется при запуске ядра; бейдж «только ядро» над схемой. ModuleClient.stop() теперь закрывает и соединение, не прошедшее рукопожатие (`run()` возвращалась после тайм-аута 10 с).

Не сделано: режим «показать текст» (владелец его не включал), подсветка пути на вкладке «Схема» (там другой набор блоков). Прогон 10 минут (параметр по ТЗ) на живом ядре со всеми службами владелец запускает сам: `python agent/tools/soak_core.py --minutes 10`.
