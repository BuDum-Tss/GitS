# 00. Архитектура: ядро и модули

Статус: согласовано 2026-10-09. Этот документ описывает целевую схему и термины. Требований к коду здесь нет: они в
ТЗ 01–21. Все ТЗ используют термины ровно в значениях из раздела «Словарь».

## 1. Цель

ГЛаДОС — агент-персонаж, который:
- максимально вживается в роль (характер ГЛаДОС, Aperture Science, эксперименты);
- отзывчив (реагирует за доли секунды) и проактивен (сам замечает поводы и говорит, но не болтает попусту);
- принимает решения и действует: управляет ПК, играет в RimWorld, монтирует видео, ведёт Telegram;
- расширяется модулями, которые включаются и выключаются, не трогая ядро.

## 2. Исходное состояние (на 2026-10-09)

Два репозитория:
- `C:\MyProjects\GitS` (GitHub `BuDum-Tss/GitS`, приватный): ассистентка. Один процесс ядра (`agent/main.py` →
  `core_service.py`): разговор (`companion.py`), маршрутизатор (`router.py`, `environments/`), зрение
  (`perception.py`), слух (`hearing.py`), микрофон (`mic_listener.py`, `stt_client.py`, `voice_id.py`), Telegram
  (`telegram_channel.py`, `telegram_user.py`), память-граф (`graph_memory.py`), дашборд на :8766 (`dashboard.py`).
  Отдельные процессы: питомец (`desktop_pet.py`, он же воспроизводит озвучку через `tts_engine`), трей (`tray.py`,
  запускает ядро, питомца и агента игры).
- `C:\MyProjects\rimworld-agent`: игра. Мод `mod/AgentBridge` (C#, порт 8765), MCP-сервер `agent/rimworld_mcp.py`,
  контуры игры (`controller.py`), комментатор, API на :8767 (`game_api.py`: `/api/game`, `/api/order`, оверлей OBS).

Связь сейчас: GitS → игра через `game_bridge.py` (HTTP :8767); игра → GitS через `speech_link.py` (`POST /api/say`,
`/api/emotion`, `/api/event`, опрос `GET /api/speech_status`); инструменты RimWorld попадают в маршрутизатор GitS через
MCP-манифест `agent/environments/manifests/rimworld.json`.

Профили уже есть в двух видах: `modes.py` (профиль = набор модулей окружений; ассистент, RimWorld, сон и заглушки) и
`profiles.py` (тон по активному окну: игра, работа, стрим, обычный). Монтажа нет: только заглушка профиля `editing`.

Прежний дизайн внимания на LangGraph (`docs/attention-graph.html`) не реализован. Его идеи (один фокус, приоритеты
P0–P3, безопасные точки прерывания, отложенные мысли) взяты в ТЗ 03, а LangGraph в ядре не используется (решение 7).

## 4. Принятые решения

| № | Решение | Почему |
|---|---|---|
| 1 | Ядро — «мозг без органов»: характер, разговор, внимание, память, разрешения, реестр, дашборд. Предметных инструментов у ядра нет, кроме общих (память, справочник, поиск в интернете, настройки, внимание). | Ядро простое и быстрое; органы меняются, не трогая мозг. |
| 2 | Модуль — отдельный процесс, который сам подключается к ядру по WebSocket и говорит по контракту ТЗ 01. Внутри модуль устроен как угодно. | Изоляция сбоев, свои зависимости (Node, мод C#), включение и выключение без перезапуска ядра. |
| 3 | Модули `voice`, `pet`, `desktop`, `telegram` живут в монорепо GitS (`GitS/modules/<id>/`) и работают в его виртуальном окружении. `rimworld-module` и `montage-module` — отдельные репозитории со своими окружениями. | Первым нужны общие настройки и тесты с ядром; вторым — тяжёлые чужие зависимости. |
| 4 | Репозиторий `rimworld-agent` переименовывается в `rimworld-module`; новый репозиторий монтажа называется `montage-module`. | Решение владельца. |
| 5 | Ассистент — обычный профиль. Профиль = конфиг (тон, модули фокуса, веса внимания, области памяти и справочника). Активен ровно один профиль; включённых модулей может быть сколько угодно; фоновые задачи модулей идут независимо от профиля. | Профиль не должен останавливать работу: рендер идёт, пока она играет. |
| 6 | Инструмент бывает `always` (виден в любом профиле: поиск, память, ответ в Telegram, статус задач, внимание) или `profile` (виден, только когда его модуль входит в активный профиль). | Отвлечься и ответить в Telegram можно из любого занятия. |
| 7 | Без LangGraph в ядре. Внимание — явный код (правила + классификатор + формула). Длинные задачи — в модулях; внутри модуля может быть любой движок (Claude Agent SDK у монтажа). | Второй оркестратор поверх SDK не окупается; контракт прячет устройство модуля. |
| 8 | Быстрый слой: GLiNER2.5-multi-Decide (287M, многоязычная) для классификации событий и реплик; Gemma (LM Studio) для речи и плана; Claude для обдумывания и долгих задач. Английская GLiNER2.5-Decide не используется: вход русский. Дообучение классификатора — позже, не в этих ТЗ. | Классификатор за десятки миллисекунд без генерации; LLM только когда нужно говорить или планировать. |
| 9 | Память трёх слоёв: личная (Graphiti/FalkorDB, уже есть), справочник (RAG по темам: вики, регламенты, документация, найденное в интернете), опыт (выводы из её собственных действий). Справочник и опыт привязаны к теме и по умолчанию видны только в профиле темы; личная память общая, с областями. | Сведения о размере комнат не засоряют память о людях, но доступны для решений. |
| 10 | Поиск в интернете — функция ядра; `lookup` сначала ищет в справочнике, потом в интернете, найденное кэширует в справочник. | Справочник растёт под реальные вопросы. |
| 11 | Важность событий динамическая: базовая оценка (классификатор + правила) × вес контекста (профиль, отправитель, состояние пользователя, временные правила, свежесть). | Иногда важнее игра, иногда Telegram. |
| 12 | Звук целиком (микрофон, STT, узнавание голосов, TTS, воспроизведение, слух системного звука) — один модуль `voice`. Воспроизведение уходит из питомца. | Перебивание и защита от эха требуют микрофон и динамик в одном месте. |
| 13 | Восприятие экрана — модуль `desktop` вместе с мышью, клавиатурой и Claude-помощником для задач на ПК. | Один владелец доступа к экрану и вводу. |
| 14 | Модули говорят с пользователем только через ядро (речь, вопросы, разрешения, синтез голоса). | Разрешения, «не отвлекать» и характер в одном месте. |
| 15 | Порядок: этап 1 — контракт и ядро (01, 02, 03); этап 2 — перенос в модули (10, 11, 12+13, 14); этап 3 — память и справочник (04); этап 4 — монтаж (20, 21). | Решение владельца. |

## 5. Словарь

- **Ядро** — процесс GitS `agent/main.py`. Единственный владелец характера, разговора, внимания, памяти, разрешений и
  речи.
- **Модуль** — процесс, подключённый к ядру по контракту ТЗ 01. Идентификатор модуля (`module_id`) — строка из
  латинских строчных букв: `voice`, `pet`, `desktop`, `telegram`, `rimworld`, `montage`.
- **Манифест** — описание модуля, которое модуль присылает при подключении: инструменты, события, подписки,
  возможности, настройки, коллекции справочника.
- **Инструмент** — действие, которое может вызвать ядро (маршрутизатор). Полный идентификатор `<module_id>.<name>`.
  Инструменты самого ядра имеют `module_id = core`.
- **Событие** — сообщение модуля «что-то произошло» (`kind` вида `<module_id>.<что>`). Все события идут через менеджер
  внимания.
- **Задача (job)** — долгое действие модуля (минуты и часы) со стадиями, прогрессом и вопросами к пользователю.
- **Профиль** — конфиг поведения (ТЗ 02, раздел «Профили»). Ровно один активный.
- **Включённый модуль** — модуль, который пользователь не выключил в настройках; его процесс запущен супервизором.
- **Модули фокуса** — модули, перечисленные в активном профиле. Их инструменты `profile` видны маршрутизатору.
- **Тема (topic)** — канал широковещательных сообщений ядра модулям (`presence`, `settings`, `profile`, ...).
- **Менеджер внимания** — код ядра, который для каждого события решает: выбросить, записать, отложить в сводку,
  сказать, прервать, действовать.
- **Фокус** — то, чем она занята сейчас (разговор, реакция на событие, тишина). Хранится стеком.
- **Канал ответа** — откуда пришло обращение и куда отвечать (голос, чат дашборда, Telegram).
- **Личная память** — факты о людях и мире из разговоров (Graphiti).
- **Справочник** — коллекции документов по темам (RAG).
- **Опыт** — выводы из её собственных действий, по темам.
- **Область (scope)** — тема, к которой привязана запись памяти, справочника или опыта: `global`, `assistant`,
  `rimworld`, `montage` и т.д.

## 6. Что остаётся как есть

- Мод RimWorld (C#) и его порт 8765; контуры игры внутри `rimworld-module`.
- Оверлей OBS на :8767 (HTTP внутри `rimworld-module`).
- Docker-сервисы: Fish Speech :8080, WhisperX :9000, FalkorDB :6380.
- LM Studio :1234 (Gemma, EmbeddingGemma).
- Разрешения (`approvals.py`, `safety.py`), батарейка Claude (`claude_battery.py`), протокол событий
  (`events_log.py`, SQLite `memory/events.db`).
- Дизайн тикетов (`docs/TICKETS_DESIGN.md`): в будущем исполнитель тикетов станет модулем `code` с задачами по
  контракту 01. В этих ТЗ не делается.
