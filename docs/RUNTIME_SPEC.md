# Спецификация каркаса рантайма: Event, Attention, Runtime

Статус: проект (целевая архитектура). Написан по схеме владельца и обсуждению 18.11.2026. Текущий код (`agent/services/attention/`,
`docs/AGENT_SCHEME.md`) этой спецификации пока не соответствует: раздел 11 описывает разницу и порядок перехода. Значения
констант это стартовые предложения, их подбирают по живой работе.

## 1. Цели и принципы

1. **Всё, что происходит, это `Event`.** Сообщение, фраза в звонке, событие игры, таймер, итог задачи. Агент видит их одним видом.
2. **Адаптеры приносят события и выполняют действия, больше ничего.** Распознавание, разбор чата, правила «мне ли это» живут в
   адаптере или его сервисе (STT и TTS внутри аудио-адаптера). Ядро не классифицирует содержимое.
3. **Срочность задаёт отправитель** (окружение знает, что для него срочно), в пределах потолка из манифеста. Ни моделей-классификаторов,
   ни формулы с весами в ядре.
4. **Внимание это небольшой автомат**: `process_event` и `on_turn`. Плавающая концентрация: агента будит событие, которое
   важнее всего, что уже ждёт и что он сейчас обрабатывает.
5. **Две явные дорожки вывода**: `say` (речь) и `text` (текст) у каждого окружения, у которого есть оба канала.
6. **Срок жизни у каждого события.** Устаревшее не обрабатывается, а сворачивается в строку «пока тебя не было».
7. **Каждое событие и каждый его переход пишется в `EventLog`** (наблюдаемость и память).

## 2. Компоненты

```
 Адаптеры                       Ядро                                            Агент
 DashboardAdapter ─┐
 DiscordAdapter ───┤ TextAdapter ─┐
 KTalkAdapter ─────┘              ├─> Event ──> process_event ──> очередь ──┐
 VCAdapter (Discord, кабели, ...) │     │            (Attention)             │ pop(EVENTS_BATCH)
        └ STT ──> AudioAdapter ───┘     └──> EventLog                        v
 core.timer ───────────────────────────>                              Runtime (Pi Harness + ChatGPT)
        ^                                                                    │ вызовы инструментов
        │                                                                    v

 (TTS ──> AudioAdapter)
```

| Компонент | Ответственность |
|---|---|
| Адаптер | принести событие в нужном виде, выставить приоритет и срок, выполнить `say` или `text`, вернуть результат событием |
| `Event` | единая запись (раздел 3) |
| Attention | `process_event`, `on_turn`, очередь, прерывание (раздел 4). Часть Runtime, один экземпляр на персонажа |
| Runtime | запуск ходов агента (Pi Harness, ChatGPT), учёт действий хода, отмена хода (раздел 5) |
| `EventLog` | запись всех событий и их состояний, запросы (раздел 8) |
| `core.*` инструменты | `core.event_log`, `core.enter`, `core.exit`, `core.timer` (раздел 7) |

## 3. Event

### 3.1 Поля

| Поле | Тип | Смысл |
|---|---|---|
| `id` | строка | уникален в журнале |
| `ts` | число | момент создания (секунды Unix) |
| `workspace` | строка | окружение-источник (`discord`, `telegram`, `rimworld`, `core` для таймеров) |
| `kind` | строка | вид, объявленный в манифесте окружения (`discord.message`, `discord.voice.utterance`, `core.timer`) |
| `sender` | объект или null | `{id, name, is_owner, is_bot}` |
| `text` | строка | готовая строка для агента (раздел 6), до 1000 символов |
| `data` | объект | структурные поля, в промпт не попадают |
| `priority` | число 0-100 | задаёт отправитель, ядро зажимает потолком вида |
| `expires_at` | число | момент, после которого событие не обрабатывается |
| `reply` | объект или null | `{tool: "discord.say" \| "discord.text", target}`: чем отвечать |
| `group_key` | строка или null | ключ слияния (раздел 4.5): например `discord:chan-2:u42` |
| `state` | перечисление | `new`, `queued`, `delivered`, `interrupted`, `expired`, `evicted`, `dropped` |
| `interrupted` | bool | событие уже попадало в прерванный ход |

### 3.2 Приоритет

Шкала 0-100, именованные уровни (отправитель берёт ближайший, может указать число):

| Уровень | Значение | Пример |
|---|---|---|
| `BACKGROUND` | 10 | фоновые фразы в групповом канале, `spoken` итог речи |
| `NORMAL` | 30 | сообщение в канале без обращения, ход игры |
| `NOTABLE` | 50 | событие игры, важное для сюжета, итог задачи |
| `IMPORTANT` | 70 | прямое сообщение, тревога окружения |
| `USER` | 100 | пользователь обратился к ней (владелец или обращение по имени) |

«Мне ли это» решает адаптер простыми правилами (имя, владелец, личный чат, ответ ей), ядро содержимое не читает.

### 3.3 Вид события в манифесте

Каждое окружение объявляет свои виды: `{kind, default_priority, max_priority, ttl_s, coalesce, reply_tool}`. Ядро при приёме
зажимает `priority` до `max_priority` вида, ставит `expires_at = ts + ttl_s`, если отправитель его не задал, и отбрасывает событие
неизвестного вида (с записью в журнал). Потолок защищает от адаптера, который объявляет всё максимальным.

Сроки по умолчанию (предложение): голосовая фраза 90 с, сообщение чата 15 мин, событие игры 60 с, таймер 10 мин, итог речи 2 мин.

## 4. Attention

### 4.1 Константы

| Имя | По умолчанию | Смысл |
|---|---|---|
| `EVENTS_BATCH` | 5 | сколько событий за один запуск |
| `QUEUE_MAX` | 30 | размер очереди |
| `WAKE_MIN` | 30 | событие ниже этого не будит простаивающего агента: ждёт `on_turn` |
| `INTERRUPT_MARGIN` | 20 | насколько событие должно превзойти занятый ход, чтобы прервать его |
| `COALESCE_MS` | 400 | окно слияния подряд идущих событий одного `group_key` перед запуском |
| `ON_TURN_S` | 20 | сколько событие ниже `WAKE_MIN` ждёт простаивающего агента (разовый таймер, не тик) |
| `FOCUS_CAP` | 60 | потолок приоритета событий окружений вне фокуса (кроме `USER` и видов с `critical` в манифесте) |
| `INTERRUPT_BUDGET` | 3 за 60 с | максимум прерываний в окне |

### 4.2 Очередь

Приоритетная: порядок по `priority` убыв., при равенстве старые первыми. `max_priority(queue)` равен приоритету первого элемента
(0 для пустой). При переполнении вытесняется самое низкоприоритетное и самое старое (`state = evicted`, считается в сводку).
Просроченные события выбрасываются при каждом обращении к очереди (`state = expired`, считаются в сводку).

### 4.3 process_event(e)

```
process_event(e):
    log(e, state=new)
    e.priority = min(e.priority, kind.max_priority); e.expires_at ||= e.ts + kind.ttl_s
    if e.workspace != focus.current and e.priority < USER and not kind.critical:
        e.priority = min(e.priority, FOCUS_CAP)      # окружение вне фокуса
    if expired(e): log(expired); digest.add(e); return
    if e.group_key and coalesce(e): return            # слито с ожидающим событием того же ключа (4.5)

    running = runtime.current_batch()                  # пусто, если агент простаивает
    top_queue = max_priority(queue)
    top_busy  = max(top_queue, max_priority(running))

    if not running:                                    # агент простаивает
        if e.priority > top_queue and e.priority >= WAKE_MIN:
            queue.push(e); runtime.trigger(queue.pop(EVENTS_BATCH), after=COALESCE_MS if e.group_key else 0)
        else:
            queue.push(e)                              # ждёт on_turn
    else:                                              # агент занят
        if has_user(running):                          # USER-ход: человеку уже отвечают
            if e.group_key and e.group_key == running_group_key and runtime.steer(e):
                return                                 # тот же человек продолжает: доливается в идущий ход
            queue.push(e)                              # иначе первым в следующей пачке, ход не прерывается
        elif (e.priority >= USER or e.priority > top_busy + INTERRUPT_MARGIN) and interrupt_budget_ok():
            runtime.interrupt(new_events=[e] + queue.pop(EVENTS_BATCH - 1))   # раздел 5
        else:
            queue.push(e)                              # будет в следующем ходе
```

Две разные реакции на «выигрыш»: простаивающего агента запускают, занятого прерывают. Занятый ход сравнивается по максимуму из
очереди и текущей пачки, чтобы событие приоритета 40 не прерывало ход по событию приоритета 80. Прерывание требует либо
`USER`, либо заметного превосходства (запас `INTERRUPT_MARGIN`); иначе событие просто встаёт в очередь первым и попадает в следующую пачку.

**USER-ход** это ход, в пачке которого есть событие `USER` (агент отвечает человеку). Такой ход не прерывается новыми событиями: продолжение того же человека
(`group_key`) доливается в идущий ход через `runtime.steer`, фраза другого человека встаёт в очередь первой. Если `steer` недоступен, продолжение
прилетает в следующей пачке. Прерывается только ход, в котором `USER` нет.

### 4.4 on_turn()

Зовёт Runtime по окончании хода. Если агент простаивает, а в очередь пришло событие ниже `WAKE_MIN`, ставится разовый таймер на `ON_TURN_S` с момента прихода
самого старого ожидающего: по нему зовётся тот же `on_turn`. Периодического тика нет; проактивные ходы без событий запускаются отдельным условием (`idle_long_enough`).

```
on_turn():
    queue.expire()
    if queue and (queue.max >= WAKE_MIN or oldest_wait(queue) >= ON_TURN_S):    # накопленное ниже WAKE_MIN сливается пачкой
        runtime.trigger(queue.pop(EVENTS_BATCH))
    elif idle_long_enough() and proactive_enabled():
        runtime.trigger_idle()                       # ход без событий: проактивная мысль, сон, рефлексия
```

Событие ниже `WAKE_MIN` не лежит вечно: либо оно уходит пачкой при ближайшем `on_turn` (по окончании хода или разовому таймеру), либо протухает и сворачивается в сводку.
Отдельных таймеров ожидания для него не нужно.

### 4.5 Слияние

События с одним `group_key`, пришедшие друг за другом в окне `COALESCE_MS` (или пока предыдущее ещё в очереди и не запущено),
сливаются в одно: тексты склеиваются в порядке прихода, берётся максимальный приоритет и самый поздний срок. Нужно для коротких
голосовых фраз одного человека и серии сообщений подряд. Окно задерживает запуск не более чем на `COALESCE_MS` и только когда `group_key` задан.

### 4.6 Сводка («пока тебя не было»)

Просроченные и вытесненные события не теряются, а попадают в одну строку сводки, которая добавляется в начало следующей пачки:
`(пропущено: 12 сообщений в «Игры», 2 события RimWorld; последнее 14:05)`. Полный список остаётся в `EventLog`.

## 5. Runtime и прерывание

### 5.1 Ход

Ход это один запуск агента (Pi Harness, ChatGPT) с пачкой событий. Runtime ведёт для хода **журнал действий**: список вызванных
инструментов со статусом (`started`, `done`, `failed`) и признаком побочного эффекта (`effect: true` у `say`, `text`, действий в играх;
`false` у чтения, `event_log`, поиска). Признак объявляет сам инструмент в манифесте.

### 5.2 Прерывание

`runtime.interrupt(new_events)`:
1. Отменяется ожидание модели и отменяемые вызовы инструментов. Инструмент с `effect: true` и признаком `interruptible` (речь) получает остановку
   (`voice.stop`/`play.stop`, причина `interrupted`). Начатое необратимое действие дожидается результата.
2. Журнал действий хода закрывается.
3. События прерванной пачки:
   - если у хода **не было ни одного завершённого действия с побочным эффектом**, они возвращаются в очередь с `interrupted = true`
     (приоритет и срок прежние) и снова попадают в пачку по приоритету;
   - иначе они не возвращаются: повторная обработка дала бы двойное действие. Вместо этого в следующий ход идёт блок «прервано» (раздел 6.3).
4. Запускается новый ход: новые события, затем лучшие из очереди до `EVENTS_BATCH`, сводка, блок «прервано» (если есть).
5. Защита от шторма: больше `INTERRUPT_BUDGET` прерываний в окне 60 с: новые события только встают в очередь (кроме `USER`: он по-прежнему прерывает,
   но подряд идущие его события сливаются по 4.5).

Форк сессии (пока агент занят, быстрый ответ параллельно) в первую версию не входит, см. открытый вопрос 3.

### 5.3 Контракт Runtime для Attention

```
runtime.current_batch() -> list[Event]      # пусто, если ход не идёт
runtime.trigger(events, after_ms=0)         # запустить ход (если идёт ход, это ошибка вызова)
runtime.interrupt(new_events)               # раздел 5.2
runtime.on_turn_end -> on_turn()            # хук
```

## 6. Представление агенту

### 6.1 Строка события

`[ЧЧ:ММ:СС] <workspace>/<kind> <отправитель>: <текст> {ответ: <tool>}`

```
[14:05:12] discord/voice Маша (владелец) в «Игры»: «Глэдос, ты меня слышишь?» {ответ: discord.say}
[14:05:30] discord/message Вася в #общий: «кто идёт играть?» {ответ: discord.text}
[14:06:00] core/timer напоминание: проверить сборку
```

Адаптер формирует `text` сам (ник и название чистятся: без переводов строк и кавычек, длины ограничены). Структурные поля агенту не
показываются; нужные ему данные адаптер включает в текст.

### 6.2 Пачка

```
(пропущено: 12 сообщений в «Игры»; последнее 14:05)         # сводка, если есть
(прервано: ход по событиям ниже начался в 14:05:08; успели: discord.say «Секунду…»; не успели: поиск в памяти)   # блок прерывания, если есть
<строки событий по убыванию приоритета, помеченные ⟲, если interrupted>
```

### 6.3 Блок «прервано»

Содержит: какие события шли, какие действия с эффектом завершены (инструмент и краткий результат), какие начаты и не завершены.
Решает ли агент продолжить прерванное, решает он сам.

## 7. Инструменты

### 7.1 Вывод окружения

- `<ws>.say(text, target?)`: речь (голосовой канал, колонки). Возвращает сразу «поставлено» и `uid`; результат приходит событием
  `<ws>.spoken` (`BACKGROUND`, срок 2 мин) с реально прозвучавшим и причиной обрыва. Это прямая замена `voice.say` и `voicechat.spoken`.
- `<ws>.text(text, target?)`: текстовое сообщение. Сбой доставки приходит событием `<ws>.delivery_failed` (`NOTABLE`).
- Окружение с одним каналом объявляет только его. `target` можно опустить, если у окружения один открытый канал; иначе обязателен.

### 7.2 core

- `core.event_log(query?, workspace?, kind?, since?, limit?)`: просмотр журнала (все события; с `workspace` только его).
- `core.enter(ws)`, `core.exit(ws)`: вход в окружение и выход. Поведение прежнее (аренда и фокус, `agent/services/spaces/`).
- `core.timer(delay_s | at, text, priority?, repeat_s?)`: создаёт событие `core.timer`, которое придёт в `process_event` в срок.
  Приоритет таймера по умолчанию `NOTABLE`, потолок как у вида `core.timer`.

## 8. EventLog

Журнал только дописывается: каждое событие записывается при приёме (`new`), каждый переход состояния (`queued`, `delivered`,
`interrupted`, `expired`, `evicted`) отдельной записью, ссылающейся на `id`. Хранит всё, что нужно памяти моментов и эпизодов.
Запросы только через `core.event_log` и API ядра. В журнал не пишутся сырые аудио и данные из `data`, помеченные адаптером приватными.
Хранение и ротация: как у текущего журнала событий ядра (`services/tracing/events_log`).

## 9. Адаптеры

- **AudioAdapter** (Discord голос, кабели, позже KTalk): приносит PCM в движок голоса (`docs/VOICE_ENGINE.md`), STT внутри; получает
  `play.*` от TTS внутри движка. Событие `discord.voice.utterance` с приоритетом по `addressed_reason` (`name`/`owner`/`one_to_one`: `USER`,
  `continuation`: `IMPORTANT`, фон: `BACKGROUND`), `group_key = <session>:<speaker>`, срок 90 с.
- **TextAdapter** (Discord текст, Telegram, дашборд): новый контракт в `gits_sdk`: `emit(kind, text, sender, priority, ttl, group_key, reply)`
  и обработчик `say`/`text`. Объявляет виды в манифесте (3.3). Распознавание «обращена ли» и приоритет считает адаптер.
- Приём события адаптером не ждёт ответа агента: быстрая реакция в звонке получается из пути `USER`: запуск без очереди и без пачки.

## 10. Метрики и наблюдаемость

`GET /api/attention`: размер очереди и её максимум, число запусков, прерываний (с причиной и бюджетом), слияний, просроченных и
вытесненных, время «приём события -> начало хода» по приоритетам и для `USER`, число пустых ходов `on_turn`. Для голоса остаётся `react_ms` движка.

## 11. Разница с текущим кодом и порядок перехода

| Сейчас | Станет |
|---|---|
| правила R1-R6 (`pipeline.py`) | приоритет и «обращено ли» в адаптере; R2 (ответ да/нет на разрешение) становится видом события с приоритетом `USER` |
| классификатор (`services/classifier/decide.py`, `input_classifier.py`) | удаляется |
| формула приоритета 0-100 с весами, решения D0-D4 (`dispatcher.py`, `kernel/scoring.py`) | `process_event` (4.3) |
| `urgency_hint` 0-5 в манифесте | `priority` 0-100 и `max_priority` по виду |
| сводка `digest.py` | сводка пропущенного (4.6) |
| `focus_stack.py`, очередь речи `speech_queue.py` | очередь речи остаётся внутри движка голоса и окружений; стек фокуса сводится к `core.enter/exit` |
| `Attention.submit`, `submit_speech`, `submit_question`, `on_job_update` | `process_event`; вопросы и итоги задач становятся видами событий |
| `voice.say`, `voicechat.utterance`, `voicechat.spoken` | `discord.say`, `discord.voice.utterance`, `discord.spoken` |
| `docs/AGENT_SCHEME.md` (Claude Agent SDK) | переписывается под Pi Harness и ChatGPT |

Порядок (каждый шаг отдельно и с тестами; старый и новый путь живут рядом, пока шаг не закончен):
1. Тип `Event`, манифест видов, рендер строки (6.1), запись в `EventLog`.
2. Attention v2 (`process_event`, `on_turn`, очередь, слияние, сводка) на заглушке Runtime; тесты раздела 12.
3. Прерывание и журнал действий в Runtime (5).
4. Контракт TextAdapter в `gits_sdk`; перенос Telegram и Discord на него; `say`/`text` в Discord (голос и текст).
5. Остальные окружения; удаление старого конвейера и классификатора.

## 12. Критерии приёмки (тесты на заглушках, без модели и сети)

1. Простаивающий агент: событие приоритета 20 не будит (ждёт `on_turn`), 40 будит.
2. Очередь `[50, 30]` и простой: приходит 60, запуск с пачкой `[60, 50, 30]`; приходит 40: встаёт в очередь.
3. Занятый ход пачки с максимумом 80: событие 90 не прерывает (нужно больше 100), `USER` (100) прерывает; ход с максимумом 40: событие 70 прерывает (запас 20 пройден строго: 70 > 60), событие 55 встаёт в очередь.
4. Прерывание без завершённых действий: события возвращаются в очередь с `interrupted = true`; с завершённым `say`: не возвращаются, блок «прервано» содержит действие.
5. Шторм: четвёртое прерывание за 60 с не приводит к прерыванию, но `USER` проходит.
6. Слияние: три фразы одного `group_key` в 300 мс дают одно событие с максимальным приоритетом и склеенным текстом.
7. Срок: просроченное событие не попадает в пачку и входит в сводку; вытесненное при переполнении тоже.
8. Потолок: событие с приоритетом выше `max_priority` вида зажимается и это пишется в журнал; неизвестный вид отбрасывается.
9. `on_turn`: накопленные события ниже `WAKE_MIN` уходят пачкой по истечении `ON_TURN_S`.
10. `EventLog`: у каждого события есть запись приёма и запись каждого перехода состояния.
11. `say`: результат речи приходит событием `spoken`, а не возвращаемым значением.

## 13. Решения и открытые вопросы

Решено 18.11.2026:
1. `on_turn` запускается окончанием хода плюс разовым таймером для событий ниже `WAKE_MIN` (4.4).
2. События окружений вне фокуса получают потолок `FOCUS_CAP` (4.3).
3. USER-ход не прерывается другим `USER`: то же лицо доливается через `steer`, другое ждёт в очереди (4.3).

Открыто:
1. Форк сессии для быстрого ответа на `USER` во время длинного хода: нужен ли, и как сливать итог в основную историю.
2. Как показывать агенту события, слитые из нескольких отправителей, если `group_key` общий для канала, а не для человека.
3. Есть ли у Pi Harness безопасный `steer` посреди хода (проверка этапа 0); без него продолжение того же человека уходит в следующую пачку.
4. Частота и стоимость проактивных ходов без событий (`idle_long_enough`).

## 14. Решения реализации (этапы 1-2, `agent/services/attention_v2/`)

Уточнения к разделам выше, принятые при реализации и подтверждённые тестами `test/attention_v2/`:

1. **Окно слияния** держит внимание, а не Runtime: для события с `group_key` ставится разовый таймер `COALESCE_MS`, по нему `runtime.trigger(batch, after_ms=0)`
   получает готовую пачку. Слияние, поднявшее приоритет выше `WAKE_MIN`, тоже будит окном.
2. **`core` вне `FOCUS_CAP`:** таймеры и события ядра потолком фокуса не режутся. Если фокус не задан, потолка нет; если `focus_getter()` вернул `None`, вне фокуса всё, кроме `core`.
3. **Сводка и блок «прервано» не передаются в `trigger`.** Runtime зовёт `attention.render_batch(events, interrupt_note)` (забирает накопленную сводку) и
   `attention.build_interrupt_note(events, actions, started_at)`. В протокол Runtime добавлен `trigger_idle()`.
4. **Манифест:** виды лежат под ключом `event_kinds` (приоритет числом или именем уровня; `coalesce` по умолчанию `false`, для старых необъявленных видов `true`).
5. **Строка события:** `workspace/<kind без префикса окружения>`, например `discord/voice.utterance`; отправитель `Имя (владелец)` или `Имя (бот)`.
6. **Возврат прерванных событий** (`requeue_interrupted`) попадает в следующую пачку, а не в новую текущую.
7. **`on_turn` молча выходит, пока ход идёт или ждёт окно слияния:** Runtime обязан очистить `current_batch()` и только затем вызвать `on_turn_end`.
8. Событие с приоритетом, равным максимуму очереди, простаивающего агента не будит; страховочный таймер `ON_TURN_S` не даёт ему залежаться.
9. В журнале зажим приоритета пишется отдельной записью `note`; `data` в журнал не попадает.

Этап 4, часть ядра:

10. **`core.timer`:** при v2 приёмник `ImpulseTimer` (`timer_emit`) превращает напоминание в событие `core.timer` (`core`, текст `напоминание: …`, NOTABLE по умолчанию, потолок IMPORTANT, срок 10 мин). Приоритет задаёт необязательный параметр `priority` инструмента `assistant.remind_self` (имя уровня или число). Без v2 путь прежний (`self.reminder` через `submit_self`).
11. **`core.event_log`** (`read_only`): `query`, `workspace`, `kind`, `since` (секунды назад), `limit` (20, не больше 100); строки «время, последнее состояние, окружение/вид, текст до 160». `data` не показывается; без v2 отвечает, что журнал выключен.
12. **`discord.say`** в ядре поверх движка голоса (`voice.*` остаются алиасами). Итог речи `voicechat.spoken` при v2 это фон и вид `passive` (`KindSpec.passive`): ждёт в очереди, но сам ход не запускает и таймер `ON_TURN_S` не заводит, при вытеснении и сроке не попадает в сводку.
13. **События голоса:** ключ `v2` тела события (`priority`, `group_key`, `reply_tool`) перекрывает вывод `from_legacy`; формат для старого внимания не менялся. Виды `voicechat.utterance` (90 с) и `voicechat.spoken` зарегистрированы в `register_core_kinds`.

RimWorld под v2:

14. **Виды `rimworld.*`** идут в v2 по умолчанию (префикс `rimworld.` в `GITS_ATTENTION_V2_KINDS`); виды объявляет манифест (`event_kinds`, строится из `core_link.EVENTS` и `EXPIRES_S`): срочность 5, 4, 3, 2, 1 это приоритет 90, 70, 50, 30, 10, потолок 90 (тревога не выглядит обращением человека, `USER` = 100 особый), срок из `EXPIRES_S` (иначе 120 с). `critical`: рейд, гибель, пожар, упавший и потерянный колонист, итог забега. `passive` и потолок 10: `colonists`, `game_started`, `run_video`, `enemy_down`, `research_done` (сами агента не будят). Серии однотипных событий (`pawn_hurt`, `enemy_seen`, `letter`...) получают ключ слияния `rimworld:<вид>` в `data.group_key`.
15. **Служебные обработчики до решения.** `V2Router` до `process_event` зовёт `Attention.run_kind_handlers(peer, event)` (публичный метод старого внимания): обработчик вида (`rimworld.colonists`: отношения и состояние колонии) забирает событие целиком, хук (`rimworld.run_ended`: метка `run_lost`) только делает побочное действие, событие идёт в v2.
16. **Бюджет прерываний.** Событие вида с `critical` прерывает ход мимо `INTERRUPT_BUDGET` (причина `critical` в `by_reason`; такие прерывания тоже заносятся в бюджет и закрывают его для некритичных). Шторм мелких прерываний не глушит рейд.
17. **Рабочий цикл.** При v2 `WorkLoop` шлёт событие `core.work_tick` (`core`, NORMAL, потолок NORMAL, срок 90 с, `coalesce` + `replace`: в очереди остаётся один, новый заменяет текст старого); `WorkLoop` не выдаёт тик, пока идёт ход по пачке или тик уже ждёт (`work_busy`). Хвосты `ResidentRuntime`: `USER_TAIL` > срочный (тревога: приоритет от 70 до `USER`, отправитель не человек, не окружение `core`; источник хода `alert`) > `WORK_TICK_TAIL` > обычный.
